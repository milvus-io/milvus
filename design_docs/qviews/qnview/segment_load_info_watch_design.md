# Segment LoadInfo Watch Design

## Background

QueryView should describe query serving topology and global load requirements.
It should not be invalidated by a physical LoadInfo change of a single sealed
segment.

The current sealed segment load path is pull based:

1. QueryNode receives a QueryView and starts preparing assigned sealed segments.
2. `QueryViewSegmentLoadScheduler` calls `GetQueryViewSegmentLoadInfo` for each
   missing segment.
3. QueryCoord forwards the request to DataCoord.
4. DataCoord packs the current `SegmentLoadInfo` and collection index metadata.
5. QueryNode loads the segment with that one-time snapshot.

This is enough for initial load, but it does not let QueryNode observe later
physical LoadInfo updates for already loaded sealed segments.

The target design removes this point lookup path. Initial sealed segment load
and later LoadInfo refresh should both be driven by one watch stream.

## Relationship With QueryView

This design must stay compatible with the existing qviews model:

- `QueryViewVersion.DataVersion` is the collection DataView version that the
  QueryView is based on. When the DataView segment set changes, the QueryView
  changes.
- `QueryViewVersion.QueryVersion` changes for redistribution, recovery, or other
  query-view-level topology changes.
- `QueryViewOfPartition.segment_ids` remains the segment assignment contract.
  Segment-level LoadInfo revision is not part of QueryView assignment.
- `QueryViewSettings` remains the global load requirement contract. It should
  not carry per-segment physical LoadInfo.

The `loadInfoRevision` in this document is a QueryNode/Coordinator watch token
for the physical LoadInfo of one already-assigned sealed segment. It must not be
mixed with `QueryViewVersion.DataVersion`.

## Principles

- A single segment LoadInfo change must not create a new QueryView.
- A global load requirement change must create a new QueryView.
- QueryViewSettings should carry global requirements, such as required fields,
  required partitions, and field-to-index requirements.
- Segment-level physical metadata update should be handled by QueryNode local
  segment runtime.
- Growing segments do not need segment-level LoadInfo update. They consume DML
  data directly and follow QueryViewSettings through QueryView lifecycle.
- DataCoord remains the authority for physical SegmentLoadInfo.

## Proposed API Shape

Replace `GetQueryViewSegmentLoadInfo` completely with a watch style API for
sealed segment LoadInfo snapshots and updates. The watch API is responsible for:

- returning the initial SegmentLoadInfo needed to load a sealed segment
- keeping the QueryNode subscription active while the segment is loaded
- pushing a new SegmentLoadInfo when the segment load revision changes

The watch key is segment scoped:

```text
{collectionID, segmentID, loadInfoRevision}
```

`loadInfoRevision` is a stable hash generated by DataCoord from the fields that
affect sealed segment loading. The first implementation can use:

```text
hash(segment_info.manifest_path, segment_info.data_version)
```

The protocol name should still be `loadInfoRevision` instead of exposing the
exact hash inputs, so DataCoord can extend the revision calculation later.

The stream should be bidirectional:

```text
QueryNode -> Coordinator:
  WatchSegmentLoadInfoRequest{
    subscribe:   [{collectionID, segmentID, loadInfoRevision}]
    unsubscribe: [{collectionID, segmentID}]
    generation
  }

Coordinator -> QueryNode:
  WatchSegmentLoadInfoResponse{
    snapshots: [{
      collectionID,
      segmentID,
      loadInfoRevision,
      loadInfo,
      indexInfos
    }]
    generation
  }
```

For initial load, QueryNode subscribes with an empty or zero revision. The
Coordinator treats that as stale and pushes the current SegmentLoadInfo
snapshot. For refresh, QueryNode subscribes with the latest loaded revision, and
Coordinator pushes a new snapshot only when DataCoord reports a newer revision.

## QueryNode Flow

QueryNode owns the subscriptions for the sealed segments it currently loads or
serves.

The watch client implementation lives in the MixCoord client package, not in
QueryNode. QueryNode receives only a local watcher handle. The watcher is
constructed with a fixed snapshot handler, maintains the local subscription
table, and owns stream reopen and re-subscribe behavior.

The local subscription table is the source of truth; when the gRPC stream
breaks, the MixCoord client watcher opens a new stream and resends all currently
loaded or loading sealed-segment subscriptions with their latest applied
revisions.

1. QueryNode receives a QueryView and determines the sealed segments assigned
   to this node.
2. For every missing sealed segment, QueryNode registers the watch key on the
   Coordinator stream with an empty or zero revision:

   ```text
   SubscribeSegmentLoadInfo{collectionID, segmentID, loadInfoRevision=0}
   ```

3. Coordinator pushes the current SegmentLoadInfo snapshot:

   ```text
   SegmentLoadInfoSnapshot{collectionID, segmentID, loadInfoRevision, loadInfo, indexInfos}
   ```

4. QueryNode updates collection index metadata with `indexInfos`, loads the
   sealed segment with `loadInfo`, and records the loaded revision.
5. QueryNode keeps the subscription active while the segment is loaded.
6. If Coordinator observes a newer revision for this segment, it pushes another
   SegmentLoadInfo snapshot on the same stream.
7. QueryNode schedules a local update for the segment.
8. If the segment is still loaded and the pushed revision is newer, QueryNode
   schedules a serialized local `Reopen | LoadIndex` update for the segment.
9. On success, QueryNode updates the local loaded revision and continues serving.
10. On failure, QueryNode keeps the old segment available and retries or reports
    local metrics. The current QueryView state is not changed.

The update path must deduplicate concurrent work. A segment should have at most
one in-flight update task.

## QueryNode Update Actions

QueryNode should treat `loadInfoRevision` as a single opaque token. The token
only answers whether the physical SegmentLoadInfo snapshot changed; it should
not encode separate data/index decisions in the public watch contract.

- `Reopen`: update data/manifest/log/stat resources of the same sealed segment.
- `LoadIndex`: load or replace index resources carried by the pushed snapshot.

The action selection is intentionally conservative:

```text
loadInfoRevision unchanged or empty:
  ignore

loadInfoRevision changed:
  Reopen(newLoadInfo)
  LoadIndex(new index infos)
```

`LoadIndex` must not bypass collection index metadata updates. QueryNode should
apply `indexInfos` to the collection runtime before calling segment-level
`LoadIndex`.

The `Reopen` and `LoadIndex` operations for the same segment must be serialized.
Concurrent snapshots should be coalesced so the segment eventually applies the
newest revision observed on the stream.

## Coordinator Flow

Coordinator should not create one goroutine, channel, or timer per watched
segment. The watch service should be implemented as batched streams and central
indexes:

```text
nodeID -> watch stream
segmentID -> subscribers[]
subscriber = {nodeID, expectedRevision, generation}
```

Coordinator responsibilities:

- Maintain subscriptions only for QueryNode-owned sealed segments.
- Support batched subscribe and unsubscribe requests.
- Scope `SubscribeInfo` to the current QueryNode stream session and remove all
  subscriptions when that stream closes.
- Push an initial SegmentLoadInfo snapshot for a new subscription whose revision
  is empty, zero, missing, or stale.
- Observe DataCoord segment metadata/index metadata changes.
- Compute or read the new `loadInfoRevision`.
- Push SegmentLoadInfo snapshots only to subscribers whose expected revision is
  stale.
- Batch push messages and apply backpressure per node stream.

Coordinator should not store complete SegmentLoadInfo for all subscriptions.
It should keep only lightweight subscription state and fetch or build complete
SegmentLoadInfo for the initial stale subscription and when a revision actually
changes.

## DataCoord Revision

The single `loadInfoRevision` must cover every field that can change the
physical loading result.
`segment_info.manifest_path + segment_info.data_version` is a reasonable first
cut only if those fields advance whenever the following resources change:

- manifest path
- data version
- storage version
- commit timestamp
- binlog, statslog, deltalog, bm25 log, text stats, and json stats identity

The revision should also cover every finished segment index input:

- finished segment index identity, including index ID, build ID, index version,
  and index store path version
- index params and type params that affect load/search behavior

If that guarantee does not hold, DataCoord should calculate `loadInfoRevision`
from the broader SegmentLoadInfo dependency set.

## Scale Cost

A naive per-segment watch object is not acceptable at ten-million segment scale.
It would create too much memory, GC pressure, reconnect cost, and scheduling
overhead.

The acceptable implementation is event driven and batched:

- no per-segment goroutine
- no per-segment channel
- no periodic full scan of all segments
- one stream per QueryNode
- batched subscribe and update messages
- central segment-to-subscriber index

For 10 million active subscriptions, expected memory is roughly:

```text
80-160 bytes per subscription in Go after map/slice/object overhead
10M subscriptions: 0.8GB-1.6GB
20M subscriptions: 1.6GB-3.2GB
```

The real number scales with replica count because subscriptions are per
QueryNode-owned segment, not per unique segment.

CPU cost is acceptable only if revision changes are event driven:

```text
register: O(number of subscribed segments)
initial snapshot push: O(number of stale subscribed segments)
single segment update: O(number of subscribers for that segment)
batch update: O(changed segments + affected subscribers)
```

Periodic scanning of all watched segments should be avoided.

## Failure Handling

- QueryNode reconnect should re-subscribe in batches with its local loaded
  revisions. Coordinator should only push snapshots for missing or stale
  revisions.
- Subscribe requests should carry a generation or stream epoch to ignore stale
  updates after reconnect.
- Update pushes should be idempotent by `{segmentID, loadInfoRevision}`.
- If QueryNode receives an older or equal revision, it should drop the update.
- If QueryNode receives an initial snapshot for a segment that is no longer
  assigned to the view, it should unsubscribe or ignore the snapshot.
- If `Reopen` fails, QueryNode should keep serving the old loaded segment and
  retry the update without changing QueryView readiness.
- If `LoadIndex` fails, QueryNode should keep serving the old segment and old
  index state, then retry the index update. QueryView readiness is unchanged.
- If the segment is released before the update is processed, QueryNode should
  unsubscribe or ignore the update.

## QueryView Boundary

This watch mechanism does not replace QueryView changes.

The following changes still create a new QueryView:

- global required field changes
- field-to-index requirement changes
- required partition changes
- segment assignment changes
- DataView segment set changes from flush, compaction, or release
- replica or node assignment changes

The following changes should be handled by SegmentLoadInfo watch and local
`Reopen`/`LoadIndex`, without changing QueryView:

- physical manifest change for the same sealed segment
- same sealed segment physical LoadInfo revision change, such as a
  `SegmentInfo.DataVersion` or manifest-path change that does not alter the
  DataView segment set
- finished index resource change for an already assigned segment
- text stats, bm25 stats, json stats, or delta resource refresh for an already
  assigned segment
