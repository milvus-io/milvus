# RecoveryStorage

Persists WAL consumer state to the catalog (etcd) and object storage. **Core invariant**: from any WAL position + the corresponding persisted state, RecoveryStorage can replay the WAL forward and recover a fully consistent in-memory state.

## Persisted State

- **WALCheckpoint** (etcd): `MessageID` (= LastConfirmedMessageID of last consumed message), `TimeTick`, `ReplicateCheckpoint` (for secondary clusters), `AlterWalState` (for WAL backend migration).
- **VChannel metadata** (etcd): Per-VChannel collection info, partition list, schema history, state (NORMAL / DROPPED / SPLITTED), plus `split_time_tick`, `split_task_id` and `retired` for a split source, and `split_genesis_checkpoint` for a split target: the target genesis replica's last confirmed message id and time tick. The flusher never recovers a target from before that position, including after a restart that comes before the SplitShard ack callback has given DataCoord a position for the target. A WAL backend switch does not rewrite it: the switch gives DataCoord a new-WAL checkpoint for every vchannel, whose tick is past the genesis, and the flusher compares the genesis by time tick first and by message id only when both ids come from the same WAL.
- **Segment assignments** (etcd): Per-segment growing/flushed status with row count and binary size stats.
- **Segment data** (object storage): Sealed segment binlog, indexes, and stats files.

## Recovery Flow

1. **Persist recovery** (`recoverRecoveryInfoFromMeta`): Load checkpoint, VChannel metadata, and segment assignments from catalog in parallel.
2. **Stream recovery** (`recoverFromStream`): Build a `RecoveryStream` from the checkpoint's MessageID to the current WAL position. Replay all messages to reconstruct in-memory state. Extract uncommitted `TxnBuffer`.

## SPLITTED VChannels

A shard split's source VChannel goes to **SPLITTED**, not DROPPED, and stays there. The source replica of `SplitShard` sets the state and records `T_switch` in `split_time_tick`. The value is read from the `SplitShardExtraResponse` the source handler stamped on the record (`_ae`), and the record's own tick is used only when it carries none. The two differ when the first fence append failed without persisting: the handler had already fenced at that attempt's tick, so the first record in the WAL is the re-drive, which reports the earlier tick. `CheckpointTimeTick` keeps the record's own tick; a later fence record of the *same* split task moves neither it nor `split_time_tick`. The record's own tick is also the source's **fence gate** (`splitFenceGate`), the tick the flusher closes the source's data sync service on (`RecordFence` sees the same record). A VChannel reloaded already SPLITTED reseeds it as `max(split_time_tick, checkpoint tick)` (`recovery.SplitFenceGate`, the same function the flusher reseeds its close gate with; the flusher reads the post-replay snapshot, so its gate can be at or past this one, never below it), and it is kept in memory rather than recomputed because a DDL replica appended to the source with no effect after the service closed moves the meta's checkpoint tick past the frozen flusher checkpoint. `DrainedPastFence` is a SPLITTED VChannel whose own flusher checkpoint has reached that gate: everything it will ever hold is persisted and every segment of it is sealed, and nothing will move the checkpoint again. DROPPED is wrong for it in two ways: a background task would call DataCoord's `DropVirtualChannel` for a channel the split coordinator retires itself, and once the row left the catalog a restart would lose the fence the [shard manager](shard-management.md) rebuilds its tombstone from.

Collection happens later and locally, on two conditions:

1. the **retire replica** — the `AlterCollection(shard_split_routing)` whose post-image no longer names this VChannel — sets `retired` (`ObserveRetire`, only legal on a SPLITTED VChannel);
2. this VChannel's **own** flusher checkpoint reaches its fence gate (`DrainedPastFence`) — the condition the flusher closed its data sync service on, so it holds once that service closed. Per VChannel, not the PChannel-wide minimum flusher checkpoint: with two splits on one PChannel that minimum is the first source's frozen checkpoint, below the second split's fence until the first source is adopted (hours, or never), and a VChannel with no flusher checkpoint yet (a data sync service just rebuilt after a restart) would pause every collection on the PChannel. `UpdateFlusherCheckpoint` wakes the persist loop the moment a pending retirement crosses its gate.

`ConsumeDirtyAndGetSnapshot` then returns a snapshot rewritten to **DROPPED with `retired` still set**, which is what actually deletes the catalog row — the catalog has no "retired and drained" concept of its own. This is emitted even when the VChannel is not dirty, because `retired` is typically persisted long before the checkpoint catches up, and without that round the row would linger in etcd forever. For the same reason a retirement that has *become collectable* counts as dirty, so the graceful-shutdown persist loop emits the removal write instead of leaving it for the next start; one that has not drained yet deliberately does not, or that loop would spin until its timeout. `dropAllVirtualChannel` reads `retired` back off a DROPPED snapshot to tell it apart from a genuine drop and skips `DropVirtualChannel` for it. Retired-but-not-yet-collected VChannels are tracked in `retiredVChannels` so the persist gate keeps re-checking even if nothing else touches the PChannel again.

Until a SPLITTED VChannel is collected, its frozen flusher checkpoint takes part in the PChannel's minimum flusher checkpoint (`getFlusherCheckpoint`). WAL truncation therefore proceeds up to it and no further — deliberately, since on restart the flusher rebuilds the source from the position DataCoord holds for it, and the WAL must keep it until the source is collected. The minimum keeps exactly that one job. The AlterWAL FLUSHING wait (`GetFlusherCheckpointByTimeTick`) asks a different question, whether everything is persisted, and skips a SPLITTED source that is `DrainedPastFence`: its frozen checkpoint would otherwise wedge the switch until adoption, and with it the RW WAL and the adoption itself. A source that has not drained yet, or has no checkpoint yet, is still waited on; a PChannel whose VChannels are all drained sources answers with the storage's own checkpoint. The AlterWAL advance stage still seeds a new-WAL position for a drained source like every other VChannel — the position DataCoord holds is decoded under the current WAL's name on the next open, so an old-WAL id left there could not be decoded; the rebuilt service acks past its reseeded gate at once and closes again. Two gauges per PChannel signal the truncation pin. Both are refreshed on each persist-loop round and deleted on close:
- `milvus_wal_recovery_oldest_splitted_vchannel_age_seconds` is the age, from `split_time_tick`, of the oldest SPLITTED VChannel not yet collected; 0 when there is none.
- `milvus_wal_recovery_truncation_lag_seconds` is now minus the minimum flusher checkpoint; absent while there is none.

A genuine DropCollection reaching a SPLITTED VChannel, retired or not, is a real drop. The meta goes DROPPED with `retired` cleared, so `DropVirtualChannel` is called.

A DDL replica addressed to a SPLITTED VChannel is still observed (the retire replica must be), but what it seals is scoped to its own VChannel: `DropPartition` seals only the partition's segments on the replica's VChannel (`flushAllSegmentOfPartition`), like the fence (`flushAllSegmentOfVChannel`), because a fenced source and one of its targets, or two sibling shards, can share a PChannel and each gets its own replica. Only `DropCollection` seals collection-wide.

A `CreateSegment` observed on a SPLITTED VChannel is skipped like one on a DROPPED VChannel: the [shard manager](shard-management.md)'s name gate refuses one on the write side, so one that reaches the recovery storage can only be a replay, and registering it would leave a GROWING assignment that nothing ever seals — the fence record, the only thing that seals the source's segments, has already been consumed. One whose TimeTick is at or before the VChannel's fence gate (`SplitFenceGate`) is the pre-fence history a restart legitimately replays (snapshot persisted SPLITTED, LastConfirmed checkpoint before the CreateSegment, the fence record replayed after it and sealing it again), so it is skipped quietly at Info; one ticked after the gate has no fence behind it (only a WAL offset reset delivers one) and is additionally reported through `detectInconsistency`.
