# Shard Management

The Shard interceptor manages per-PChannel collection/partition/segment in-memory metadata and assigns each incoming DML message to a growing segment. All state is purely in-memory, should always keep consistent with underlying-WAL; on WAL open, it is recovered from the [RecoveryStorage](recovery-storage.md) snapshot.

See [Collection Messages](../message/message-semantic-collection.md) for per-message semantics and the messages handled by this interceptor.

## Seal Policies

Growing segments are sealed when any registered policy triggers. See `internal/streamingnode/server/wal/interceptors/shard/policy/seal_policy.go` for the full list of policies.

## VChannel Registration

The manager's registration map is keyed by **collection id**, one entry per collection per PChannel, and the entry names the VChannel it describes. Every operation that consults it must match on that name, not just the collection id: a fenced source's slot is freed immediately, so a later VChannel of the same collection can hold the entry, and an operation that ignored the name would answer for, fence, or tear down the wrong shard.

Registration admission is enforced here rather than assumed of the caller:

- `CheckIfVChannelCanBeCreated` — `ErrCollectionExists` for an idempotent replay of the same VChannel; `ErrVChannelConflict` when another VChannel of the collection holds the entry, which the interceptor turns into a rejected append. Consulted by the **target replica** of a SplitShard broadcast, which registers a new VChannel the way CreateCollection does. Refusing rather than warning is deliberate: the newcomer would otherwise skip its own registration and inherit the incumbent's state — including a fenced source's fence, leaving the new shard permanently unwritable.
- `CheckIfVChannelCanBeWritten` — `nil` only when this PChannel holds that exact VChannel and it is live; `ErrVChannelFenced` when the name has a fence tombstone (a DML write becomes `SHARD_FENCED`; the proxy's refresh-and-retry on it is not implemented yet); `ErrCollectionNotFound` otherwise, which is terminal. The redo interceptor asks it too: its partition lookup runs outside the VChannel lock, so a fence can land between two of its iterations and make the lookup fail exactly as for a VChannel never held; on that failure it re-checks the name and answers `SHARD_FENCED` for a fenced VChannel instead of an unrecoverable error.

The interceptor applies `CheckIfVChannelCanBeWritten` **once**, in `DoAppend`, for every collection-keyed message: DropCollection, CreatePartition, DropPartition, ManualFlush, SchemaChange, AlterCollection, TruncateCollection, CreateSegment and Flush. There is no per-handler name check. A message addressed to a VChannel this PChannel does not hold appends with no shard-state effect, with three exceptions:
- DropCollection still releases the addressed VChannel's function-runner key.
- ManualFlush appends with an empty segment list on a fenced source, and is refused on a VChannel that was never held.
- CreateSegment and Flush are refused either way: `SHARD_FENCED` on a fenced source, unrecoverable on a VChannel that was never held. They are not broadcast replicas but messages this node's own segment workers append, and the workers stop on either error. Their handlers look a partition up by (collection, partition), which a split target of the same collection on the same PChannel shares, so a late CreateSegment of a fenced source would otherwise be applied to the target. `ShardManager.CreateSegment`/`FlushSegment` re-check the name under the manager lock as well. A Flush from the old architecture is exempt.

Insert and Delete keep their own admission. See the table in [Collection Messages](../message/message-semantic-collection.md).

## Split Fence Tombstones

`SplitShard`'s **source replica** fences the VChannel and tears its registration down in **one** critical section — a reader must never see the registration gone without the tombstone in its place. The handler does this **before** it appends the fence record, and keeps the fence whatever the append returns. An append error does not prove the record is absent: the WAL adaptor returns a canceled or expired context, or a fenced WAL term, as it gets it, and the backend may already have written the record. If the fence followed the append, such a record would sit in the WAL while the VChannel kept taking DML after its tick. If the append did fail, DML on the VChannel is refused with `SHARD_FENCED` until the broadcaster's re-drive lands. That re-drive takes the same-task re-fence path below and reports the first attempt's tick. If the node restarts before the re-drive, the fence is lost with the node's memory, nothing recorded it, and the re-drive is a genuine first fence. The fence itself consists of:

- a `SplitFence{TimeTick, TaskID}` is recorded in `fencedVChannels`, keyed by VChannel **name**. That tombstone is the only place a fence is ever recorded, since the registration it would otherwise live in is gone. It is what answers a stale proxy route, and what `GetSplitFence` returns to a re-sent fence.
- the registration is removed and every partition manager of the collection flushed and dropped. Dropping a partition manager (here, and on DropCollection and DropPartition) cancels its segment-alloc worker, so no CreateSegment for the source keeps being retried. Nothing on the source needs it: no DML follows the fence, and the growing segments were sealed by `FlushAndFenceSegmentAllocUntil` while the message was being built (this message *is* the seal record; there is no separate ManualFlush). Freeing the slot here is what lets a successor VChannel of the same collection be registered on this PChannel without waiting for a routing commit.
- the VChannel's WAL **function-runner key** is released here too, exactly as DropCollection does, and the target genesis allocates one for the new VChannel (`allocFunctionRunners`). It has to be the fence and not the retirement: `Close` releases by *registered* VChannel, and a fenced source has no registration left to be found under, so a key held until adoption would leak across any WAL close in between. Release is idempotent, so a re-driven fence releasing again costs nothing.

A second fence record of the **same** task appends again but moves nothing: `T_switch` is the tick of a task's *first* fence record, every fence record of one task seals the same data (the VChannel took no DML in between), and the source handler reports that recorded tick back as the replica's `SplitShardExtraResponse` — set on the append result and stamped on the record itself (`message.SetAppendExtra`), so an ack from either side carries it and the coordinator records the first tick. Raising it would be unsafe: the source's data sync service may already have drained past the first fence and closed, so a later `T_switch` could never drain. A fence record reaching a VChannel that **another** task fenced (a recorded task id of zero counts as another task) is refused on the append path with `SHARD_FENCED` carrying the recorded tick and task id; it must never move a fence it did not place. The task id is what lets a caller tell its own retry from a fence some other split placed. A record whose own `split_task_id` is zero is refused as unrecoverable before any of this, and nothing is sealed or fenced.

On WAL open the map is rebuilt from the RecoveryStorage snapshot: every VChannel the snapshot reports as **SPLITTED** seeds a tombstone (`split_time_tick`, `split_task_id`) and is *skipped* when building the registration map, so a restart lands on exactly the state the fence left — including when a live successor already holds the collection's slot. A snapshot holding two **live** VChannels of one collection is a placement the coordinator should never have made — the split's own source no longer collides, since it is skipped; the map keeps one deterministically by name (the lexicographically smaller wins, so every replay of the snapshot answers the same) and logs an Error, so a restart cannot leave a live shard unwritable at random.
