# ASYNC_LOAD 调度开销采样（2026-11-13）

## 结论

当前最明显的瓶颈是全局调度锁的竞争和等待/唤醒成本，优先级高于 RequestContext 或元数据分配优化。组内 FIFO 并不意味着大多数提交都避开全局锁：本基准每个序号只有 4 条任务链，组经常被取空，空任务场景约 69%–72% 的提交进入全局发布锁。

这不是 perf 结果。机器 `perf_event_paranoid=4`，`perf record -e cycles:u` 和 `cpu-clock:u` 均被拒绝，且没有免密 sudo。实际使用已安装的 gperftools `libprofiler.so` 做 250 Hz 用户态 CPU 采样，并用独立临时插桩测量锁等待/持有时间。没有修改生产实现。

## CPU 样本

16 个 worker。下面是 pthread mutex lock/unlock、`__lll_lock_wait/wake` 对应的互斥样本占比，使用 flat 归属，未叠加调用者占比。内联函数展开后按最外层函数归属指令，避免重复计数。

| 场景 | 样本数 | mutex 等待/唤醒等路径占比 |
| --- | ---: | ---: |
| 默认 Folly，64 链，空任务 | 3,067 | 0.00% |
| Folly + 元数据适配器，64 链，空任务 | 2,799 | 0.00% |
| 分组队列，64 链，空任务 | 11,933 | 46.79% |
| 分组队列，4096 链，空任务 | 13,801 | 52.06% |
| 分组队列，64 链，10 μs 工作量 | 11,929 | 6.29% |
| 分组纯队列，深度 4096 | 14,834 | 68.50% |

这是 CPU 样本位置，不是线程睡眠时间比例，也不能直接等同于可优化掉的端到端时间。Folly 两项 0.00% 只表示没有采到上述函数，不能解释成整个执行器完全无锁。真实内核栈、cache miss、cacheline 迁移和调度器 off-CPU 时间均未取得。

空任务分组场景里，按函数名称归类的 RequestContext/RequestData 直接样本约 7%，malloc/free/new/delete/tcache 直接样本约 3%。函数可能内联，分配也不全属于上下文，因此这些只是热点线索，不是精确的组件成本分摊。下面的对照实验比这个分类更有说服力。

## 元数据对照

同一个未开启采样的 `-O3 -g1 -fno-omit-frame-pointer` 二进制，固定此前的 16 核亲和性，每个场景交错运行 5 次取中位数。单位为百万次任务执行/秒。

| 任务链 / 每次工作 | Folly 默认队列 | Folly + 相同元数据适配器 | 分组队列 |
| --- | ---: | ---: | ---: |
| 64 / 0 μs | 3.275 | 3.066 | 1.007 |
| 4096 / 0 μs | 3.168 | 3.051 | 0.902 |
| 64 / 10 μs | 1.250 | 1.216 | 0.788 |

加元数据的 Folly 版本仍使用 LoadExecutor 和 RequestContext，但绑定的组指针为空，不包含分组队列的 weak_ptr 锁定、共享组引用计数以及组状态更新。它用于估计适配器/上下文的影响，不能完整剥离分组版本的所有元数据成本。

这轮空任务中位数下降约 4%–6%，明显小于分组队列与 Folly 的差距。重复范围和原始记录见 controls.csv；共享主机存在其他负载，不能把几百分点差异当成稳定常数。

## 全局调度锁测量

仅在 `/tmp` 副本里替换三处调度锁 guard。每个线程每个调用位置每 1024 次获取锁抽样一次，用 steady_clock 记录调用 lock 前、获得锁后和 unlock 前的时间。未开启 CPU profiler。每个场景执行 4,194,304 个任务。

| 场景 | 入队发布平均等锁 | 入队平均持锁 | 出队选组平均等锁 | 出队平均持锁 | 入队获取发布锁次数 / 任务数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 64 链，空任务 | 4.73 μs | 0.24 μs | 4.53 μs | 0.28 μs | 2,875,521 / 4,194,304 ≈ 68.6% |
| 4096 链，空任务 | 6.27 μs | 0.27 μs | 6.12 μs | 0.35 μs | 3,011,055 / 4,194,304 ≈ 71.8% |
| 64 链，10 μs | 1.75 μs | 0.23 μs | 1.64 μs | 0.27 μs | 3,213,578 / 4,194,304 ≈ 76.6% |

每项等待/持有时间是各次抽样的算术均值。各线程等待相互重叠，不能把它们相加当成总运行时间。持锁时间包含读取时钟的扰动；等待时间也可能包含线程被抢占。周期性抽样可能有偏差。统计包含启动、退出和基准自检产生的少量锁调用。

入队锁调用次数不等于实际 push_heap 次数：迟到的生产者可能看到组已发布或又被取空，获取锁后什么也不做。本轮没有进一步统计这些分支。可以确认的是，发布锁不是只在加载操作开始时获取一次。

## 有限自旋锁对照

临时副本仅把调度锁替换为 Linux `PTHREAD_MUTEX_ADAPTIVE_NP`。该锁采用自适应的有限自旋，仍可休眠；未更换注册表锁，未调整排序或队列算法。两个版本都不开启 profiler 或锁时间插桩，随机交错各运行 5 次。所有运行退出 0，并执行原有排序/生命周期自检。

| worker / 链数 / 工作 | std::mutex，百万次/秒 | adaptive mutex，百万次/秒 | 变化 |
| --- | ---: | ---: | ---: |
| 1 / 64 / 0 μs | 1.235 | 1.236 | 基本持平 |
| 16 / 64 / 0 μs | 0.978 | 0.881 | −9.9% |
| 16 / 4096 / 0 μs | 0.880 | 0.894 | +1.5%，运行范围重叠 |
| 16 / 64 / 10 μs | 0.796 | 0.884 | +11.0% |
| 16 / 64 / 100 μs | 0.129 | 0.129 | 基本持平 |

结果不足以支持直接替换生产锁。它说明“临界区很短，所以换自旋就一定更快”在这里不成立。临时版本未进行完整并发测试或 sanitizer 验证，也不作为可合并实现。

## 后续优化顺序

1. 优先分析组频繁取空和重新发布造成的全局同步：补充实际入堆/出堆次数、多个生产者重复争取发布锁的次数，判断能否减少无效争锁。任何优化都必须保留“组对消费者可见后才发布 semaphore 许可”的约束，并验证与消费者取空并发时不丢任务。
2. 在实际 load/reopen 中测组深度和上述频率。如果真实组内有较多并发任务，基准里频繁取空的模式可能并不代表生产。以真实任务时长、调度 CPU、排队延迟和总加载时间决定是否值得继续。
3. 暂不直接分 bucket 锁。严格 priority/load_seq 选择仍需跨 bucket 协调，而且消费者可能集中竞争最早的同一组；分散注册表或 FIFO 的锁不能解决已测到的全局选组热点。分 bucket 需要独立算法验证，不能由这份数据推导它一定更快。
4. 元数据分配和共享引用计数作为第二优先级。当前有成本，但对照不支持把它们视为主要原因。没有硬件计数器证据，不把缓存行共享或 CAS 重试认定为瓶颈。

## 记录和复现边界

[原始记录目录](benchmarks/async-load-profile-20261113/) 包含 CSV、锁时间日志、CPU top/cumulative、临时插桩、构建命令、源码快照、校验和和采样脚本。`summary.json` 保存未四舍五入的汇总。原始 `.prof` 文件保存在同目录但被 .gitignore 忽略；`/tmp/async-load-profile` 保存本轮二进制和所有临时文件。

环境沿用前次 Xeon Gold 6338、同 NUMA 的 16 个 CPU、worker nice 19、GCC 12。采样二进制只增加调试信息和 frame pointer。正式的 6 次 CPU 采样、3 次锁插桩、45 次元数据对照、50 次锁类型对照按阶段串行运行；前期探索记录保存在 `/tmp/async-load-profile/exploratory`，不混入表格。主机并未隔离，存在其他工作负载。

构建脚本和库路径依赖本机 Conan 缓存及 `/tmp/load-seq-include`。脚本中的工作目录为 `/tmp/async-load-profile`，源码输入路径指向当前 worktree；重跑前应核对保存的源码快照/校验和，或将输入改为快照，不能直接用于跨机器复现。`run.py` 中自动 pprof 符号解析在本机过慢；正式采集通过 `final-run.py` 完成，符号通过 `symbolize.py` 的 addr2line 批量解析。CPU 采样包含启动/退出、自检和依赖库线程的少量样本，不是仅调度区间的精确分账。

没有真实 segment load/reopen、I/O admission 或完整 Milvus 集成验证，没有生产代码变更。本轮结论适用于调度基准，不能据此宣称加载端到端改善。
