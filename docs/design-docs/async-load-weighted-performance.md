# 32:8:1 CPU 加权调度实验

测试日期：2026-11-19。基于已统一使用 ThrottledLifoSem 的加载执行器，改为 URGENT:HIGH:LOW = 32:8:1。本轮没有修改 Folly、Proto、资源限流器或 Search 生产调用链，也没有启用资源积累保护。

## 实现与适用范围

CPU 队列按三级分别维护就绪组堆。在现有取任务锁内选择优先级，每轮分配 32、8、1 次任务取出机会，空队列跳过并放弃剩余份额；整个队列空闲后重置轮次。同级继续按 load_seq、组内 FIFO 排序。正在执行的任务不被抢占，份额不是 CPU 时间、字节数或 segment 数。Folly 的空任务退出标记单独计数，只在所有普通队列为空时取出，防止加权 LOW 轮次让 worker 提前退出并遗留任务。

保留 Folly CPUThreadPoolExecutor、addWithPriority 和 ThrottledLifoSem，getNumPriorities 返回 3。新增本地 AsyncLoadPriority 枚举和执行器重载；默认池使用 HI/MID/LO 分别承载 Urgent/High/Low。原 Proto HIGH/LOW 调用保持兼容。自定义外部执行器保持旧 HIGH 映射，不承诺三级能力。

资源等待依旧是原来的严格 HIGH/LOW。因此这里仅验证 CPU 就绪任务的进展，不能宣称已经解决端到端饥饿，也不能宣称 Search 已接入 URGENT。

## 全部 HIGH：新增机制本身的成本

对照为改动前严格队列与加权队列，两者均使用 ThrottledLifoSem。7 场景 × 2 版本 × 5 轮，共 70 次，全部正常退出、window 数和 checksum 一致。随机交错，同一 NUMA 16 个物理核，保留每个 segment 的时间戳。表中为各指标 5 轮中位数，响应时间从提交到完成，active 从首次执行到完成。

| 场景 | 整批严格→加权 ms | 变化 | 响应 P50 ms | active P50 ms |
|---|---:|---:|---:|---:|
| CPU | 2228.2 → 2216.8 | -0.5% | 1180.3 → 1167.4 | 34.5 → 34.2 |
| CPU / I/O 混合 | 486.9 → 485.7 | -0.2% | 303.0 → 301.9 | 302.0 → 301.3 |
| I/O | 1106.2 → 1126.1 | +1.8% | 561.9 → 589.4 | 561.3 → 588.8 |
| 前 1/4 为大 segment | 775.7 → 777.7 | +0.3% | 587.8 → 595.3 | 587.2 → 594.6 |
| 后 1/4 为大 segment | 777.4 → 783.6 | +0.8% | 301.7 → 309.3 | 300.1 → 308.7 |
| 每 2 ms 到达 | 488.2 → 484.3 | -0.8% | 241.7 → 222.3 | 209.1 → 184.6 |
| 单 segment | 319.0 → 317.1 | -0.6% | 319.0 → 317.1 | 319.0 → 317.0 |

本机共享环境每组仅 5 轮，不把几个百分点的差异解释为已证实的优化或稳定回归。各场景都保留结果，不只列改善项。

## 三级混合加载：公平性与 URGENT 延迟的交换

为单独比较选择策略，额外构建了三级严格优先级控制版本：它与加权版使用相同的三级分组和本地优先级 API，仅把选级函数改为永远选择最高就绪等级。64 个 segment 按 ID 模 3 分配 Urgent、High、Low；所有资源申请仍为 HIGH，并保留 load_seq 排序，以隔离 CPU 调度。3 场景 × 2 版本 × 5 轮，共 30 次全部正常退出且 checksum 一致。

| 场景 | 整批严格→加权 ms | URGENT 响应 P50 ms | HIGH 响应 P50 ms | LOW 响应 P50 ms |
|---|---:|---:|---:|---:|
| CPU | 2230.8 → 2227.4 | 493.7 → 591.2 | 1214.5 → 1258.9 | 1902.6 → 1899.5 |
| CPU / I/O 混合 | 490.7 → 479.4 | 291.9 → 288.7 | 300.4 → 299.8 | 307.1 → 306.8 |
| I/O | 1121.4 → 1106.0 | 545.8 → 541.7 | 580.4 → 567.6 | 614.9 → 598.5 |

CPU 场景整批基本不变，URGENT 响应 P50 从 493.7 ms 增至 591.2 ms（+19.8%）。HIGH 首个 segment 完成从 886.8 ms 提前到 293.0 ms，LOW 从 1575.4 ms 提前到 1123.4 ms。给低级别持续执行机会，不意味着其所有分位数都会变好；HIGH 的响应 P50 在此场景反而略升。

混合/I/O 场景较少持续占满 CPU，且仍有共同的资源限流，不能从其耗时反推 32:8:1 的资源份额。

## 持续积压的 co_await 测试

每级维持 2 × worker 数个协程，每完成一段固定计算就 co_await co_reschedule_on_current_executor，再次进入同一队列。达到全局 41,000 个工作片段时停止。分别测 1/16 worker、每片段 0/2000 次运算、每组 5 轮，共 40 次尝试；没有运行真实存储 I/O。

单 worker 的全部 20 次运行正常退出。严格版每轮均为 URGENT 41,000、HIGH 0、LOW 0；加权版每轮均为 32,000、8,000、1,000。16 worker 下，计数截止与多线程实际执行次序会产生少量边界差异，原始每级计数保留在 saturated-runs.json。

这验证持续就绪时 CPU 队列不会让整个 HIGH/LOW 类别饿死，不提供某一个 segment 的完成时限。执行中的任务可能很长，同级较小序号也仍有优先权。

## 超时与验证限制

最终 40 次饱和协程与 10 次 tiny 测试均正常退出。tiny 波动较大，不将其百分比作为实际加载收益。

修正前的异常样本保存在 before-barrier-fix。绑定 CPU 后由 GDB 启动捕获到现场：工作计数已输出，主线程在 DefaultExecutorState 析构 / Folly joinStoppedThreads 中等待，剩余 worker 仍在基准的 std::latch::wait 中。原先启动屏障按引用捕获，极短负载可在部分 worker 从 wait 返回前结束并销毁屏障。已将 ready/release/done 改为由使用者捕获 shared_ptr，延长同步对象生命周期；没有为此修改生产队列或 Folly。

修正后重新编译所有基准，前后版本使用同一修正后的测试程序；重新执行全部加载与协程对照，以最终结果替换前一批统计。最终 40 次饱和协程、10 次 tiny、100 次 segment 加载均正常退出，未再出现屏障等待超时。超时样本不通过强制退出或成功重试掩盖，历史记录保留。旧有其他程序的退出问题是否同因，未逐个验证。

10 项 AsyncLoadExecutorTest 随机重复 10 轮，共 100 次通过；新增测试覆盖配额、同级序号/FIFO、空级跳过、空闲轮次重置、URGENT 协程恢复。现有测试覆盖并发入队、组重用、执行器切换、线程池扩缩等。独立队列检查验证了退出标记在 128 个普通任务之后取出，并覆盖任务销毁、组回收与跨队列上下文；git diff --check 通过。

本轮为独立构建，未完成完整 Milvus 集成构建、真实 Search/segment 加载、最终版本 sanitizer 验证。不要将“CPU 调度模拟未显示严重开销”表述为生产验收通过；本轮测试屏障生命周期问题已修正并复测，真实系统行为仍需验证。
