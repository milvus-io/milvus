# MEP: Index-backed Matryoshka Representation Learning

- **Created:** 2026-09-24
- **Author(s):** @jamesgao-jpg
- **Status:** Under Review
- **Component:** Index
- **Related Issues:** #53821
- **Released:** TBD

## Summary

Add index-backed Matryoshka Representation Learning (MRL) to one dense vector
field without changing its schema dimension. The field retains its original
dimension `D`, while the complete existing index behavior runs on the first
`mrl_dim` dimensions, denoted by `k`.

When `with_mrl_refine=true`, the indexed paths perform one additional rerank of
the returned candidates using the original `D`-dimensional vectors owned by
Segcore. Raw vectors stay outside the index and are not serialized with it.

The same configuration applies to persistent indexes, growing and sealed
interim indexes, and raw brute-force search. Collection creation, insertion,
and search APIs remain unchanged.

## Motivation

MRL embedding models place useful information in vector prefixes. Searching a
shorter prefix can reduce index storage and distance-computation cost, but
Milvus currently uses the field dimension for every index and brute-force
search path.

Users need one field and one index configuration that:

- builds and searches an existing index at a selected prefix dimension;
- preserves the full vector for retrieval and optional final refinement;
- works consistently across persistent, interim, and brute-force paths; and
- keeps each base index's existing coarse-search and refinement behavior.

This design introduces an index-level MRL wrapper instead of adding MRL logic
to every individual index implementation.

## Public Interfaces

MRL adds two index-build parameters to the existing index parameter map:

```python
index_params.add_index(
    field_name="embedding",
    index_type="AUTOINDEX",
    metric_type="COSINE",
    mrl_dim=1024,
    with_mrl_refine=True,
)
```

| Parameter | Default | Meaning |
| --- | --- | --- |
| `mrl_dim` | omitted or `-1` | Disable MRL. A value satisfying `0 < mrl_dim < dim` enables MRL and selects prefix dimension `k`. |
| `with_mrl_refine` | `false` | After indexed search at `k`, rerank its returned IDs with the original `D`-dimensional raw vectors. A valid `mrl_dim` is required. |

The parameters are stored with the logical index. Changing either parameter
requires dropping and rebuilding that index. Search requests cannot override
them, and no candidate-budget or refinement-type parameter is added.

AutoIndex accepts and preserves both parameters while resolving its existing
physical index configuration. The resolved base-index parameters are validated
at dimension `k`.

The first release has this support matrix:

| Area | Supported | Rejected |
| --- | --- | --- |
| Vector type | `FLOAT_VECTOR`, `FLOAT16_VECTOR`, `BFLOAT16_VECTOR` | Binary, sparse, INT8, and vector-array fields |
| Metric | L2, IP, COSINE | Other metrics |
| Index type | Any registered Knowhere index that accepts the selected type, metric, and configuration at `k` | Combinations rejected by existing Knowhere validation |
| Search | Ordinary top-K | Range Search, `AnnIterator`, and iterator-v2 |

## Design Details

### Behavior invariant

The wrapped base index receives `k`-dimensional build and query data. Its
complete existing behavior, including any internal coarse search and internal
refinement, runs at `k`.

| Configuration | Indexed search result |
| --- | --- |
| MRL disabled | Existing `D`-dimensional behavior |
| MRL enabled, `with_mrl_refine=false` | Return the completed `k`-dimensional base-index result |
| MRL enabled, `with_mrl_refine=true` | Rerank exactly the IDs in the completed base-index result using the original `D`-dimensional query and raw vectors |

The final MRL refinement does not expand the candidate set. For example, an
index that already performs 3-bit coarse search and 8-bit refinement performs
both stages at `k`; optional MRL refinement then uses raw vectors at `D`.

### Class and ownership view

```text

|                              v                                      |
|                 +--------------------------+                         |
|                 | MRLIndexNode             |                         |
|                 |                          |                         |

|       | Existing IndexNode |   | DataViewIndexBase     |             |
|       |                    |   |                       |             |
```

`MRLIndexNode` implements Knowhere's existing `IndexNode` interface. Milvus
therefore continues to store one `knowhere::Index<IndexNode>` in
`VectorMemIndex` or `VectorDiskIndex` regardless of whether MRL is active.

| Member | Responsibility |
| --- | --- |
| `source_dim_` | Original field dimension exposed to Milvus |
| `mrl_dim_` | Prefix dimension used by `base_index_` |
| `base_index_` | Existing index implementation executing at `k` |
| `refine_index_` | Optional `DataViewIndexBase` operating at `D` |
| `view_data_` | Runtime-only accessor to Segcore-owned raw vectors |

### Parameter propagation

The existing metadata and build request structures remain the transport for
the two new keys.

| Boundary | Existing artifact | Change |
| --- | --- | --- |
| SDK to Proxy | `CreateIndexRequest.ExtraParams` | Carry `mrl_dim` and `with_mrl_refine` |
| Proxy | User and resolved index parameters | Validate the combination; preserve both keys through AutoIndex resolution |
| DataCoord to DataNode | Logical-index metadata and build request | Reuse existing index-parameter propagation |
| QueryNode to Segcore | Field and load-index metadata | Reuse existing index-parameter propagation |
| Milvus C++ | `CreateIndexInfo` | Store both values and an optional runtime `ViewDataOp` |
| Knowhere | `CreateMRLIndex` | Wrap the already-created base `IndexNode` when `0 < k < D` |
| Brute-force plan | `SearchInfo::BruteForceIndexParams` | Copy both values from field index metadata |

No new RPC field is required. Existing Segcore build and search call shapes
remain unchanged outside metadata parsing, wrapper construction, raw-data
binding, and unsupported-search checks.

### Build and data preparation

Knowhere dense kernels require tightly packed rows. Merely changing a dataset's
dimension would use the wrong row stride, so dataset-backed paths copy each
row's first `k` values into a contiguous prefix buffer.

| Path | Source | Prefix preparation | Final-refiner state |
| --- | --- | --- | --- |
| Growing interim index | Segcore `ConcurrentVector` | Copy each build or add batch into a contiguous `N * k` buffer | Record count and COSINE norms from the original `N * D` batch |
| Sealed interim index | Segcore loaded vector column | Copy each build batch into a contiguous `N * k` buffer | Record count and COSINE norms from the original `N * D` batch |
| Persistent index | Local `D`-dimensional build file | Stream bounded batches into a temporary `k`-dimensional file and pass its path to the base index | Record count and COSINE norms while reading the original file |

The temporary persistent-build file is removed on success or failure. It keeps
working memory bounded but temporarily duplicates the prefix on local disk.
Dataset-backed build and search paths can temporarily hold both original and
prefix buffers.

### Search paths

| Path | `with_mrl_refine=false` | `with_mrl_refine=true` |
| --- | --- | --- |
| Persistent index | Search `base_index_` with a copied `NQ * k` query | Complete the `k`-dimensional base-index search, then use `DataViewIndexBase::SearchWithIds` at `D` |
| Growing or sealed interim index | Same wrapper behavior as the persistent index | Same wrapper behavior with a Segcore callback for the corresponding raw storage |
| Raw brute force | Copy base and query prefixes and run existing brute force at `k` | Run existing brute force once at `D` |

Full-dimensional brute force is already exact over the segment. Its refinement
branch therefore searches at `D` directly instead of performing a redundant
prefix search followed by a second exact pass.

MRL Range Search and iterator entry points return an unsupported error for
indexed and brute-force paths in the first release.

### Raw-vector ownership and callback binding

`DataViewIndexBase` borrows vectors through `ViewDataOp`; neither it nor
`MRLIndexNode` owns the raw vector column.

| Search path | Segcore owner | Callback binding |
| --- | --- | --- |
| Growing interim | Per-field `ConcurrentVector` | `FieldIndexing` captures the vector storage when creating `VectorMemIndex` |
| Sealed interim | Loaded vector column | `InterimSealedIndexTranslator` maps compact IDs to column rows |
| Persistent | Loaded segment column | `ChunkedSegmentSealedImpl` creates the accessor and passes it through `CreateIndexInfo` before index deserialization |

The persistent `SealedIndexTranslator` keeps its existing constructor shape.
The callback is runtime context stored in `CreateIndexInfo`; it is not
discovered by Knowhere and is not serialized. Segcore must keep the callback's
backing column valid for the searchable index lifetime.

An active MRL wrapper reports `HasRawData=false`, even when its base index owns
exact prefix vectors, because a prefix cannot reconstruct the original field
value. Load-resource planning therefore retains the full-dimensional vector
column for retrieval and optional refinement.

### Serialization

The MRL wrapper serializes an envelope around the base index:

| Entry | Serialized data |
| --- | --- |
| MRL metadata | Format version, `source_dim`, `mrl_dim`, data type, and `with_mrl_refine` |
| Base index | Complete serialization produced by the wrapped `IndexNode` |
| Refiner state | Dimension, data type, metric mode, vector count, and COSINE norms when needed |
| Raw vectors and callback | Never serialized |

Child `BinarySet` entries use distinct prefixes. During deserialization,
Milvus constructs the wrapper with current configuration and the runtime
callback, then Knowhere validates the stored metadata and restores the base
index and refiner state.

Persistent disk indexes store the wrapper metadata and optional refiner state
alongside the existing base-index files. The initial implementation disables
index mmap for active MRL indexes because the wrapper does not implement the
file-deserialization entry point.

### Validation and failure behavior

- `with_mrl_refine=true` without a valid `mrl_dim` is rejected at index
  creation.
- Invalid dimensions, vector types, and metrics are rejected before the base
  index build begins.
- Existing base-index validation remains authoritative after replacing `dim`
  with `mrl_dim` in its train configuration.
- Refined search fails if the raw-vector callback is absent or its backing
  column is unavailable.
- Deserialization rejects mismatched dimensions, data types, refinement mode,
  format version, or invalid COSINE norm state.
- Temporary prefix files use scoped cleanup on build failure.

## Compatibility, Deprecation, and Migration Plan

An omitted `mrl_dim`, or `mrl_dim=-1` with refinement disabled, preserves
existing behavior. Existing indexes and collections require no migration.
Collection schemas, inserted vector values, retrieval, and search request
formats are unchanged.

MRL parameters are immutable index-build properties. To change or disable MRL,
drop and rebuild the affected index. The original field data remains at `D`,
so rebuilding does not require reinsertion.

MRL index blobs contain a new Knowhere wrapper format. All nodes that may build
or load these indexes must run a version containing the MRL implementation
before users create them. Downgrading to a version without the wrapper requires
dropping MRL indexes first and rebuilding compatible indexes afterward.

Cardinal requires no MRL-specific change. A Cardinal-backed base index receives
the same normal `k`-dimensional dataset or file that any other wrapped base
index receives.

## Test Plan

- Knowhere unit tests compare prefix-index results with a direct
  `k`-dimensional reference index, with and without final refinement.
- Knowhere serialization tests cover wrapper metadata, base-index entries,
  refiner count, COSINE norms, runtime callback rebinding, malformed state,
  missing top-K, and missing callback handling.
- Proxy and parameter-validation tests cover both parameters, defaults,
  dimensions, data types, metrics, refinement dependencies, and AutoIndex
  preservation.
- Milvus C++ index tests cover wrapper construction for memory and disk indexes,
  build/load round trips, and full-dimensional retrieval ownership.
- Growing and sealed interim tests cover callback row mapping and the three
  supported dense vector types.
- Brute-force tests compare prefix-only search and full-dimensional refinement
  behavior with direct reference searches.
- Search tests verify that Range Search and iterator paths reject active MRL.
- Regression tests verify that indexes without MRL parameters retain existing
  build, load, search, mmap, and raw-data behavior.
- CI runs formatting, compilation, Go tests, C++ tests, integration tests, and
  the dependent Knowhere test suite.
- Performance validation measures index size, build time, search latency,
  recall, prefix-buffer memory peaks, temporary disk use, and raw-column
  residency for representative `D` and `k` values.

## Rejected Alternatives

- **Separate prefix and full-dimensional fields:** this duplicates user data
  and indexes and makes the application coordinate candidate search and
  reranking.
- **Map `mrl_dim` to SAQ configuration:** dimension reduction and scalar
  quantization have different semantics and support matrices.
- **Expose `mrl_refine_type`:** the first release has one final-refinement
  contract: Segcore-owned raw vectors through `DataViewIndexBase`.
- **Serialize raw vectors into the MRL index:** this duplicates the field data
  and makes index files own data already persisted by Milvus.
- **Modify every base index:** a generic `IndexNode` wrapper keeps existing
  index implementations and their internal search behavior unchanged.
- **Use a strided prefix view:** current dense index and brute-force inputs
  assume tightly packed rows; a view that only changes dimension would produce
  incorrect row addressing.
- **Support Range Search and iterators immediately:** their result cardinality
  and incremental refinement contracts require separate design and testing.
