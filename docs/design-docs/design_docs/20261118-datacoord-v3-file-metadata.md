# StorageV3 file metadata in DataCoord

## Implementation plan

1. Final flush of an ordinary L1 segment. Install the writer's cumulative statistics and checkpoint row count before releasing the four FieldBinlog lists. Require a published StorageV3 manifest and enough statistics to replace the lists. Keep the legacy path for older writers and segments. Use the recorded column-group formats for format compaction and column-group memory sizes for index and TEXT/JSON task estimates. Compare flush metadata with catalog reload, including row count, sizes and task estimates.
2. TEXT and JSON stats. Pass the complete worker result to the manifest transaction. Cache the field, build, version, format and size once the manifest owns the files. Read files from the segment's selected manifest revision when an interface needs paths, including snapshot export and legacy recovery. Preserve TEXT complete keys and JSON paths relative to the field stats directory, including nested names. Keep catalog-only historical stats usable. Exercise restart, failed publication, retries and file resolution.
3. Ordinary vector and scalar indexes. Cache the build identity, index version, file count and whether the manifest holds the build. Read the revision recorded in `SegmentInfo.ManifestPath` for manifest-backed builds. Read the exact catalog row for catalog-backed builds. Preserve a replaced build's exact file names at publication so rollback can restore it after earlier manifest revisions have been reclaimed. For manifest indexes, make orphan GC retain the whole live build/version directory, including protected migration aliases. Leave unlisted files in a retained directory until that version retires. Preserve build state, snapshot, import, segment ownership and upload-age checks. Test both path layouts, retries, replacement, retirement and file lookup errors.

Run targeted Go regression tests for each change, then run the affected packages together with the repository's dynamic/test tags and disabled inlining. These changes affect local coordination state and storage cleanup. WAL payloads and replicated collection operations retain their existing contracts.

## Compatibility and verification

- A final flush can release its file lists only after the checkpoint and cumulative writer statistics have been applied to the private segment copy. The manifest version must be positive. A missing column-group summary or an unknown format preserves the old lists. Schema materialization updates the format and size summaries when it adds groups.
- A committed TEXT or JSON field keeps its metadata and a `files_in_manifest` marker. On reload, a historical row with inline names is compacted only if the selected manifest confirms its build and version. Copy and restore may remap build IDs, so older snapshot placeholders are checked against the target field's version and relative files. A catalog-only list remains available.
- New snapshots carry the cumulative V3 segment statistics in the per-segment manifest mapping. Restore uses those statistics even when the copy result has empty or partial FieldBinlog lists. Snapshot readers continue to accept old mappings with no statistics. Older snapshots without either usable statistics or file lists cannot supply a historical segment size.
- `SegmentInfo.ManifestPath` selects the current published revision for index file reads. Load, snapshot creation, migration and cleanup verify build ID, index ID, index version, layout and file count. A newer object-store revision can still be awaiting catalog publication. If a segment advances during snapshot or QueryView assembly, DataCoord can recapture the descriptor and its indexes together. A copy target becomes readable after its segment publishes the verified worker result. Restoring a completed snapshot uses its recorded segment revision.
- A replacement commit obtains the displaced build's keys from its open transaction. After catalog publication, the existing build record retains those keys for rollback or cleanup. A rollback with neither a current entry nor retained keys reports an error before updating the catalog. On restart, catalog rows and the segment's published manifest determine the recoverable builds. Orphan GC can classify a retained V3 build/version directory and its migration aliases using build metadata. Retiring a build retracts its current entry when applicable and deletes known files. Subsequent orphan scans collect extra files.
- Regression tests compare a final flush with catalog reload, resolve nested JSON and TEXT files from a real manifest, exercise old catalog rows, verify file lookup after replacement and rollback, and distinguish neighboring version directories. A five-process local StorageV3 cluster exercised HNSW, a JSON INVERTED scalar index, JSON-key stats and a TEXT index after snapshot restore. The restored collection had 3,000 rows. The JSON filter selected 600 rows, vector search succeeded, and a TEXT_MATCH query in a temporary integration variant found the expected 429 rows. A term inserted after the snapshot returned zero rows.
