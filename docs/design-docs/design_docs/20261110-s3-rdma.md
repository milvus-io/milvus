# MEP: S3 RDMA Data Transfer for Object Storage

- **Created:** 2026-11-10
- **Author(s):** @jteh-cloudian
- **Status:** Draft
- **Component:** Storage
- **Related Issues:** TBD
- **Released:** TBD

## Summary

On Linux, Milvus replaces the upstream AWS SDK for C++ with Cloudian's RDMA-enhanced fork
(`aws-sdk-cpp 1.11.921+rdma`). With this fork, object payloads move between Milvus memory and an
RDMA-capable S3 service over RDMA instead of being streamed through the HTTP/TCP connection. The
S3 control path (authentication, request signing, headers, status codes) is unchanged.

Two consumers benefit:

1. **`MinioChunkManager`** calls the fork's explicit `PutObjectRDMA` / `GetObjectRDMA` APIs,
   so data moves directly from or to the caller's buffer.
2. **Arrow and milvus-storage**, which link the same `AWS::aws-sdk-cpp-s3` target, get RDMA
   transparently through the fork's standard `PutObject` / `GetObject` path, with no source
   changes.

The fork's RDMA transport is built on NVIDIA's `libcuobjclient` (shipped with CUDA 13.4). A new
script extracts those libraries so that CPU builds do not need a CUDA installation and GPU builds
keep their existing CUDA version.

## Motivation

Milvus is storage-bandwidth bound in several paths: loading sealed segments and indexes on
QueryNode, writing binlogs and index files from DataNode/IndexNode, and compaction. On the
current TCP path:

- Every object read or write goes through the kernel network stack. At 100–400 Gb/s this costs a
  lot of CPU, and that CPU is taken from search and index building.
- Latency and throughput per connection are limited by TCP, which makes large index loads slow
  to complete.

S3-compatible object stores that support RDMA (for example Cloudian HyperStore with S3 RDMA,
built on NVIDIA's cuObject server) can place object data directly into registered client memory.
This removes the copies and most of the CPU cost. Support needs to be added at the SDK layer
because both Milvus's own chunk manager and Arrow's S3 filesystem use the AWS SDK.

## Public Interfaces

There are no changes to the Milvus API, proto, SDK or `milvus.yaml`.

Observable changes:

| Area | Change |
|---|---|
| Build dependency (Linux) | `aws-sdk-cpp/1.11.921+rdma@milvus/dev` from a local Conan recipe in `internal/core/thirdparty/aws-sdk-cpp/`, replacing `aws-sdk-cpp/1.11.921@milvus/dev`. Non-Linux platforms are unchanged. |
| Build dependency (Linux) | Headers and libraries from `libcuobjclient`, `libcufile` and `cudart` (CUDA 13.4), downloaded by `scripts/download_cuobj.sh` into `internal/core/thirdparty/cuobj/`. |
| Builder images | `libibverbs-dev` is added to the CPU and GPU builder images. |
| Runtime images | `libnuma1`, `libibverbs1`, `ibverbs-providers` and `librdmacm1` are added to the CPU and GPU Milvus images. `libcufile*` and `libcuobj*` are installed into the Milvus library directory by `scripts/install_milvus.sh`. |
| Runtime environment | Setting `S3RDMA_CLIENT_ALWAYS_USE_TCP=true` (read by the fork) disables RDMA and sends object contents over TCP. This also applies to Arrow storage operations. |
| Runtime environment | RDMA buffer registration needs an unlimited (or large enough) `memlock` limit for the non-root `milvus` user. cuFile is configured with `/etc/cufile.json`. |
| Deployment | `scripts/standalone_s3_rdma.sh` starts standalone Milvus against a remote RDMA-capable S3 endpoint configured in `user.yaml`. |
| Metrics | No new metrics. The existing `internal_storage_request_latency_{get,put}` histograms now measure the RDMA calls on Linux. |

## Design Details

### Architecture

```text
                    Milvus C++ core (segcore / index / storage)
                 ┌────────────────────────────┬──────────────────────────┐
                 │ MinioChunkManager          │ milvus-storage / Arrow   │
                 │  PutObjectBuffer           │  S3FileSystem            │
                 │   → PutObjectRDMA(buf,len) │   → PutObject/GetObject  │
                 │  GetObjectBuffer           │     (transparent RDMA)   │
                 │   → GetObjectRDMA(buf,len) │                          │
                 └──────────────┬─────────────┴────────────┬─────────────┘
                                │   AWS::aws-sdk-cpp-s3    │
                                ▼   (cloudian-aws-cpp-sdk-s3)
                 ┌───────────────────────────────────────────────────────┐
                 │ Cloudian aws-sdk-cpp 1.11.921+rdma                    │
                 │  HTTP/TCP: signing, headers, status ──────────────┐   │
                 │  data: libcuobjclient → libcufile → ibverbs/rdmacm│   │
                 └───────────────────────────────────────────────────┼───┘
                                │ RDMA (RoCE / InfiniBand)           │ TCP
                                ▼                                    ▼
                               RDMA-capable S3-compatible object store
                               (Cloudian HyperStore 8.2.6.5)
```

### Chunk manager data path

`MinioChunkManager::PutObjectBuffer` and `GetObjectBuffer` are the only places Milvus writes or
reads whole objects to or from a caller-owned buffer of known size. On Linux only:

- **Put:** builds `Aws::S3::Model::PutObjectRDMARequest` (bucket, key, and an optional CRC32C
  checksum algorithm, as before) and calls `client_->PutObjectRDMA(request, buf, size)`. No
  request body stream is created.
- **Get:** builds the existing `GetObjectRequest` and calls
  `client_->GetObjectRDMA(request, buf, size)`. The fork writes into `buf` directly.

### Arrow and milvus-storage

Arrow's S3 filesystem and milvus-storage link `AWS::aws-sdk-cpp-s3`. The Conan recipe maps that
target to the fork's `cloudian-aws-cpp-sdk-s3` library, so they get the fork's transparent RDMA on
standard `PutObject`/`GetObject` calls. Streaming/ranged access patterns go through the fork's
internal buffering; they do not get the application-buffer behavior that the explicit `*RDMA`
calls give the chunk manager.

### Build integration

- **Conan recipe** (`internal/core/thirdparty/aws-sdk-cpp/conanfile.py`): fetches
  `cloudian/aws-sdk-cpp` tag `1.11.921+rdma` with a pinned SHA-256. It removes the fork's
  `find_package(CUDAToolkit 13.1 REQUIRED)`, so a CUDA toolkit is not required, and passes
  `NVIDIA_CUOBJ_INCLUDE_DIR` from the Conan conf `user.aws-sdk-cpp:cuobj_include_dir`. The build
  fails early if `cuobjclient.h` is not found there. The dependency set (aws-c-*, aws-crt-cpp,
  openssl, libcurl), the component options and the CMake target names match the upstream recipe,
  so consumers see the same `AWSSDK` package.
- **`internal/core/conanfile.py`**: requires the `+rdma` version on Linux and the existing pinned
  revision elsewhere.
- **`scripts/3rdparty_build.sh`**: on Linux, runs `download_cuobj.sh` if the headers are missing,
  exports the local recipe, and passes the conf to every `conan install` variant.
- **`scripts/download_cuobj.sh`**: reads NVIDIA's Ubuntu 22.04 apt index for the host
  architecture (`x86_64` or `sbsa`), selects the newest `libcuobjclient`, `libcufile` and
  `cuda-cudart` 13.4 packages (runtime and `-dev`), checks each `.deb` against the SHA-256 in the
  index, extracts it with `dpkg-deb` without installing it, and fails if any library symlink is
  left dangling. `CUDA_REPO_URL` can point it at a mirror.

### Failure cases

| Case | Behavior |
|---|---|
| No RDMA NIC, no RDMA-capable endpoint, or `S3RDMA_CLIENT_ALWAYS_USE_TCP=true` | Object contents go over TCP through the same SDK calls. This fallback is provided by the fork. |
| `memlock` too low | RDMA memory registration fails. The deployment script sets `--ulimit memlock=-1:-1`; Helm/Operator deployments must do the same. |
| Missing `libibverbs`/`librdmacm`/`libnuma` at runtime | `libcuobjclient` fails to load and Milvus does not start. The runtime images install these libraries. |
| S3 error (auth, missing key, checksum mismatch) | Returned through the normal S3 outcome and raised with `ThrowS3Error`. |
| Object larger than `size` on Get | Same as before: callers pass the size from `GetObjectSize`. |

## Compatibility, Deprecation, and Migration Plan

- **Data format:** unchanged. Objects written over RDMA are ordinary S3 objects and can be read by
  older Milvus versions and by non-RDMA clients, and the reverse is also true.
- **Upgrade/rollback:** no metadata or configuration migration. Rollback means deploying an image
  built with the upstream SDK.
- **Platforms:** macOS and non-Linux builds still use the upstream SDK and code path. Linux
  builds (CPU and GPU, x86_64 and aarch64) always use the fork; there is no build switch.
- **GPU builds:** cuObject libraries come from the extracted CUDA 13.4 packages, independent of
  the CUDA version Knowhere/RAFT is built against.
- **Operational:** The environment variable `S3RDMA_CLIENT_ALWAYS_USE_TCP=true` disables RDMA at
  runtime.

## Test Plan

- **Unit:** The SDK fork has unit tests for RDMA data transfer integrity.

## Rejected Alternatives

- **Adding S3 RDMA support directly to MinioChunkManager.** This involves modifying
  `PutObjectBuffer` and `GetObjectBuffer` to add the RDMA token and process the responses.
  It would duplicate the processing that is already present in the Cloudian's RDMA-enhanced
  fork. This also leaves Arrow using TCP for S3 data transfers.
