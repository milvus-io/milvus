# REST v2 unknown request field policy

Issue: [milvus-io/milvus#52311](https://github.com/milvus-io/milvus/issues/52311)

## Goal

Catch misspelled or misplaced API fields consistently across REST v2 without
breaking existing clients by default. For example, a top-level `groupParams`
object is not part of the search API and must not silently appear to enable
grouping when an operator has selected strict validation.

This is independent of validating the values of supported group parameters.
FunctionChains, grouping, and other business logic are unchanged.

## Conventions adopted and adapted

[Go's JSON decoder](https://pkg.go.dev/encoding/json#Decoder.DisallowUnknownFields)
ignores unknown struct fields by default and offers opt-in rejection.
[Kubernetes server-side field validation](https://kubernetes.io/docs/reference/using-api/api-concepts/#field-validation)
demonstrates a production Ignore/Warn/Strict migration model.

Adopt the staged acceptance/warning/rejection principle and the per-request
override of a server default. Adapt the request selector to Milvus REST v2 as
the `unknownFieldPolicy` query parameter, with a backward-compatible default
and the existing REST error envelope. Do not copy Kubernetes's default policy,
duplicate-body-field rejection, or response status conventions. This is a
Milvus-specific contract, not a universal HTTP standard.

Use [RFC 6901 JSON Pointer](https://www.rfc-editor.org/rfc/rfc6901)
for unambiguous field paths rather than ambiguous dotted paths.

## Configuration and observable behavior

```yaml
proxy:
  http:
    v2UnknownFieldPolicy: ignore
```

The configuration accepts `ignore`, `warn`, or `strict` (case-insensitive,
surrounding whitespace trimmed). It defaults to `ignore` and supplies the
policy only when the request has no override. Invalid values fail configuration
initialization instead of silently disabling the policy. This first version is
restart-required, not hot-reloadable.

Any REST v2 request can set `?unknownFieldPolicy=ignore|warn|strict`. The
request value overrides the server setting, including `ignore` over a server
default of `strict`; the server setting is not an enforcement floor. Request
values are case-insensitive and whitespace-trimmed. An empty, invalid, or
repeated query value returns HTTP 200 / REST code 1100 before the business
handler. Existing body binding errors still take precedence. REST v1 and gRPC
do not read this parameter. No request header or CORS allow-list change is
needed.

| Policy | Unknown API field after successful binding |
| --- | --- |
| ignore | Execute the existing handler, without scanning for unknown fields. |
| warn | Execute the existing handler unchanged; add `X-Milvus-Warning`. |
| strict | Abort before the business handler with HTTP 200 and REST code 1100. |

Warn does not change the JSON response or guarantee business success. A request
can receive a warning and then fail existing business validation. The response
header is exposed to browser clients using `Access-Control-Expose-Headers`.
Existing SDKs are not assumed to display
this custom header automatically. Operators must arrange client/header
inspection during migration. No high-cardinality metric labels or unbounded
per-request logs are introduced.

Responses generated by outer middleware (for example timeouts or admission
rejection) may omit the handler's warning.

Only the first unknown field in wire order is reported. A diagnostic contains
the field path, never the associated value, and is ASCII-quoted for header
safety. Paths are bounded to 256 bytes plus a truncation marker; a truncated
diagnostic is not a complete JSON Pointer. Subsequent unknown fields may become
visible after the first is fixed. Invalid configuration or missing internal
body state is a system error, not a client input error.

The response header is the client notification contract; clients are responsible
for reading it. Server-side observability is separate: the registered counter
`milvus_proxy_restful_unknown_field_requests_total` counts one request when the
scanner finds an unknown field in warn or strict mode. Its labels are `node_id`,
the bounded route-derived `function_name`, and `policy`; field paths and values
are never metric labels. Ignore does not scan or increment this counter, and
binding failures precede it. A rate-limited INFO log records the method, policy,
and bounded first field path, never its value. This does not classify warnings
as business failures or change existing request/failure counters.

## One enforcement boundary

All endpoints registered by `HandlersV2.RegisterRoutesToV2` use `wrapperPost`.
The server default is sampled once, then a request override is resolved and
applied there:

```text
existing authentication/admission/timeout middleware
  -> existing JSON binding and required/type validation
  -> request policy override (or server default)
  -> centralized unknown-field policy
  -> existing business handler
```

No endpoint-specific key lists or checks are added. The scanner derives fixed
field names from the bound request's Go type, with a shared type-only reflection
cache. A single-pass byte cursor walks the already-validated cached JSON,
decoding only keys with the standard library and skipping opaque values
lexically. It neither rewrites values nor invokes custom decoders again.
The current REST v2 request structs use explicit fields. The scanner retains
their JSON tags and exact/case-folded name matching, without implementing general
Go embedded-field dominance or invalid-tag fallback. Adding promoted embedded
fields to these request schemas would require revisiting this boundary and its
binder compatibility tests.

No process-global Gin decoder flag is changed. Such a flag would affect REST
v1 and would not adequately cover custom decoding. No new request structs or
generated mocks are needed.

### Special decoding paths

* **Insert and upsert:** the existing metadata-only binder validates the body
  and caches the original bytes without materializing the entity data array.
  The policy checks the original `CollectionDataReq` API envelope, including
  fixed `fieldOps` entries, while treating `data` as opaque. It does not inspect
  the binder's private array-marker type or lose large integer/JSON values.
* **Import:** `ImportReq.UnmarshalJSON` retains option/null/autocommit handling.
  After it succeeds, the common scanner checks the original API type against
  cached bytes. Unknown envelope keys cannot disappear inside the custom decoder.
* **Hybrid search and FunctionChains:** fixed subsearches, chain operations,
  expression structures, and aggregation structures are recursively checked.
  Function parameters and expression literals remain open values.
* **Open-name maps with fixed values:** names such as
  `searchAggregation.metrics.<user-name>` and resource group names are free;
  their struct-valued contents are checked. For example, an invalid metric
  member is reported as `/searchAggregation/metrics/price.avg/typo`.

Custom decoders added in future must keep API field names represented by the
request type or explicitly revisit this common schema boundary. A decoder that
accepts undocumented aliases not represented by its type would need additional
compatibility work; enabling Gin strict decoding would not solve that either.

## Compatibility boundaries

* REST v2 only; REST v1, gRPC, health, metrics, and unrelated HTTP endpoints
  retain their current behavior.
* All current REST v2 request families are covered, not only search: collections,
  databases, entities, partitions, users/roles/privileges, indexes, aliases, import,
  snapshots, external collection jobs, resource groups, files, and analyzer APIs.
* Entity fields, dynamic fields, user JSON, RawMessage, and interface-valued
  payloads remain under collection schema and existing business validation.
* Open dictionaries such as `searchParams`, `exprParams`, `properties`,
  `options`, and function params do not acquire a generic key allowlist.
  This policy therefore does not detect every typo inside an open dictionary.
* Existing supported compatibility fields (including legacy `params`),
  capitalization behavior, duplicate known keys, numeric decoding, required
  fields, nulls, and value validation are not redefined.
* Syntax/type/required/custom-decoder failures precede unknown-field diagnostics.
  Authentication and admission errors may precede decoding as they do today.
* Duplicate objects are scanned in wire order: an unknown member in an earlier
  occurrence is still unknown, even if a later duplicate replaces its value.
  Duplicate keys themselves are not rejected.

## Cost and rollout

Ignore avoids the extra scan. Warn/Strict add raw JSON traversal; open data is
not decoded into a second object graph, but finding the end of a large raw
array still costs CPU proportional to its bytes. Nested objects are consumed
once rather than repeatedly extracting and rescanning entire subtrees. Request
cancellation is checked at structure boundaries, not periodically inside long
opaque strings or values. This is not a claim of zero-cost strict validation.
Benchmarks cover small/large entity batches and deep aggregation chains with a
large leaf, comparing allocations and CPU.

Roll out the server default `ignore -> warn -> strict` only after clients have
been audited. A client can opt into `warn` or `strict` while the server remains
at `ignore`, or opt out of a stricter server default for one request. Existing
SDK versions do not send this query parameter automatically. In particular,
bulk-import SDK requests containing cloud-only envelope keys can still fail
under a server default of `strict`; the default remains `ignore`, and this
incompatibility is accepted rather than silently allowing those keys in strict
mode. Request-level override does not make an unaudited client strict-compatible.
Restart all proxies with a consistent configuration; mixed old/new proxies or
mixed policies during rolling upgrades can produce inconsistent acceptance.
Rollback is configuration `ignore` plus restart, with no stored-data migration.
Forward-compatible clients intentionally sending future API fields should stay
on ignore/warn until the server supports those fields.

## Verification

1. Configuration tests: default, each mode, normalization, invalid startup.
2. Scanner tests: nested arrays and struct-valued maps, opaque user data,
   RawMessage, duplicate/case-folded keys, explicit-field selection against
   Go JSON decoding, nulls, path escaping, header injection/size, no value mutation,
   deep structures, opaque out-of-range numeric literals, and cancellation.
3. Boundary tests in all three modes: actual Gin binder and wrapper with a
   business callback; strict must never invoke it on unknown fields, while
   ignore/warn must preserve the response and cached original body. Cover
   request-over-server precedence in both directions, no-override defaults,
   invalid/empty/repeated query values, and warning-header behavior.
4. Decoder regressions: import custom options, insert/upsert metadata-only data,
   fixed fieldOps, FunctionChains plus group parameters, aggregation maps,
   and preservation of prior binding errors. Representative existing SDK import
   create/progress bodies must reject cloud-only keys under strict before the
   business handler, while an explicit request-level ignore override accepts
   the same bodies.
5. Route sweep: use the actual router registration, discover every route, submit
   a binding-valid superset fixture with a leading unknown field, and require
   strict rejection on each route without any backing proxy. This catches a
   route accidentally bypassing the common gate without maintaining a route list.
6. Existing HTTP-server package tests in default ignore mode; separate scanner
   race checks and large-entity allocation benchmarks.
7. Warning propagation through the actual timeout middleware, preserving the
   normal response body and exposing the warning header to browser clients.
8. Registered counter collection through the actual binder and wrapper: known
   requests and binding failures do not increment it; multiple unknown fields
   increment it once in warn/strict, with only bounded labels.

Items 1-8 exercise in-process HTTP entry points, not a live Milvus cluster.
Targeted live verification can use an isolated Tencent Cloud deployment with
the policy set to strict, a valid baseline request, and the same request with an
unknown fixed API field. Confirm that the latter returns REST code 1100 and
does not perform the operation. This does not establish compatibility of every
existing REST test with strict mode. Keep the existing CI deployments at their
backward-compatible default ignore policy. Verify warning-header propagation
through the deployment's gateway separately; in-process tests cannot establish
how an external gateway handles custom headers.
