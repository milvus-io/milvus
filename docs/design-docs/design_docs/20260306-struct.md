# Struct Data Type

## Summary

Introduce a new `Struct` data type in Milvus as the element type of `DataType.ARRAY`, enabling an **Array of Struct** composite data model — logically binding multiple scalar and vector fields together within each array element.

## Motivation

Users frequently need to store multiple related embeddings and metadata per row. For example, a video may contain multiple clips, each with its own embedding and tags. Currently this requires either splitting data across multiple collections or using unstructured JSON fields, sacrificing query efficiency and schema enforcement.

The Struct type allows vectors to exist inside array elements. Prior to Struct, `DataType.ARRAY` could not contain vector fields. With Struct, Milvus natively supports:

- **Embedding List** — each row contains multiple vectors, with multi-to-multi vector similarity search using metrics such as MaxSim.
- **Element Filter & Element-Level Search** — filtering and searching at the granularity of individual array elements. Element Filter evaluates filter conditions independently on each array element; Element-Level Search performs vector search at the granularity of each embedding in the Embedding List. The two can be used together.
- **Match Family** — a set of array-level quantified filtering operators (ANY / ALL / LEAST / MOST / EXACT), supporting same-element multi-field matching for Struct arrays (nested semantics).

Additionally, Struct enforces strong typing on sub-fields (types, dimensions, etc.) via `StructFieldSchema`, making it safer and more efficient than JSON-based approaches.

## Design

### Schema

Struct can only be used as the `element_type` of a `DataType.ARRAY` field. Each Struct field is defined by a `StructFieldSchema` that specifies its sub-fields.

**Allowed sub-field types:** scalar types (INT64, VARCHAR, FLOAT, etc.), scalar ARRAY, and vector types (FLOAT_VECTOR, etc.).

**Not allowed:** nested Struct, JSON, primary key, or auto-id.

A vector sub-field is a vector field of the collection: it counts toward the vector field limit and can be the collection's only vector field. A search without `anns_field` (gRPC or REST) defaults to it when it is the only vector field, and DataCoord waits for its index, like any other vector field's, before it counts a segment as indexed.

The Struct field's row-level `nullable` value propagates to every sub-field;
sub-fields cannot set row-level `nullable` independently. A Struct object
inside the array cannot itself be null. Within a Struct sub-field,
`element_nullable` may be set for scalar `Array` and `ArrayOfVector` fields.
Nested scalar `Array<Array<T>>` sub-fields use a `TypeSchema` whose root and
second Array nullable flags equal the sub-field's propagated `nullable` and
`element_nullable`; the scalar leaf nullable flag is independent. These
new-format Array kinds are not allowed as top-level fields.

```python
struct_schema = client.create_struct_field_schema()
struct_schema.add_field("clip_embedding", DataType.FLOAT_VECTOR, dim=128)
struct_schema.add_field("clip_id", DataType.INT64)
struct_schema.add_field("clip_tags", DataType.ARRAY,
                        element_type=DataType.VARCHAR, max_capacity=10)

schema.add_field("clips", datatype=DataType.ARRAY,
                 element_type=DataType.STRUCT,
                 struct_schema=struct_schema, max_capacity=1000)
```

REST v2 describes a sub-field as the whole stored column, as its existing `structFields` requests do: a single-level scalar sub-field is `dataType` `Array` with the scalar type as `elementDataType`, a vector sub-field is `dataType` `ArrayOfVector`, and a nested `Array<Array<T>>` sub-field has `dataType` and `elementDataType` both `Array` and a `typeSchema` whose `arrayElement` is the inner array and `arrayElement.arrayElement` the leaf. An element-nullable sub-field takes `elementNullable`, which for a nested sub-field is the inner array. pymilvus and the Go SDK describe one struct element and leave the outer array out. In the Go SDK, a sub-field of an `entity.StructSchema` describes one struct element: an `Array` sub-field with a scalar `ElementType` is stored as `Array<Array<T>>` and written with a `ColumnXxxArrayArray`, and the sub-field's `Nullable` is its `element_nullable`. See [REST v2](./20260709-element-level-null.md#rest-v2) for how the three clients write each kind of sub-field, and [Client APIs](./20260709-element-level-null.md#client-apis).

**Proto changes:**

```protobuf
message CollectionSchema {
    ...
    repeated StructFieldSchema struct_fields = 9;
}

message StructFieldSchema {
  int64 fieldID = 1;
  string name = 2;
  string description = 3;
  repeated FieldSchema fields = 4;
  repeated common.KeyValuePair type_params = 5;
}
```

### Storage

Each sub-field of a Struct is physically stored as an independent column, typed as `ARRAY of <field_type>`. For example, a `clip_id` (INT64) sub-field under a Struct array is stored identically to a regular `ARRAY<INT64>` column: one serialized proto `Binary` per row. An element-nullable scalar sub-field is stored as an Arrow `list<T>` and a nested `Array<Array<T>>` sub-field as `list<list<T>>`, formats a top-level Array field never uses; see [element-level null](./20260709-element-level-null.md#representation-and-data-flow).

This design avoids defining a new composite physical type and reuses the existing columnar storage and serialization infrastructure. The system maintains a metadata mapping from the Struct field name to its set of physical columns (e.g., `"clips" -> {clip_embedding, clip_id, clip_tags}`).

In a growing segment, each sub-field column copies every insert or load batch into per-batch memory blocks of the growing chunk and keeps one view per row: `ArrayView` for legacy scalar Arrays, `ArrayValueView` into one `ColumnarArrayChunk` per batch for native-list scalar Arrays, and `VectorArrayView` for vector Arrays. See [Recursive Array Columnar Layout](./20260724-recursive-array-struct-column-layout.md#growing-segments).

The sub-field set can change after collection creation. `AlterCollectionSchema.AddRequest` appends a sub-field to an existing Struct array field when the field name is the sub-field path (`clips[clip_tags]`); the new sub-field must be `element_nullable=true`. For old rows, a null Struct row stays null, while a non-null row with N elements receives N null elements in the new sub-field. A sub-field can be dropped by its stored name (`clips[clip_tags]`) or field ID, except when it is the last sub-field, the collection's last vector field, or referenced by a function, or when every sub-field left would be one added after the Struct was created. See [Adding and dropping sub-fields of an existing struct array field](./20260930-struct-subfield-evolution.md) for the current schema-evolution rules.

### Vector Index (Embedding List Index)

The metric decides how a vector sub-field (`ArrayOfVector`) is indexed. Under an embedding-list metric (the MAX_SIM family), all vectors across array elements within a row are flattened and passed to **knowhere** along with per-row offset information, and the index treats each row as one embedding list:

- `float*` — all vectors concatenated
- `offsets` — cumulative element counts per row, e.g., row sizes [3, 2] yield offsets `[0, 3, 5]`

| Aspect | Supported |
|--------|-----------|
| **Index types** | HNSW, IVF_FLAT, DISKANN |
| **Metric types** | MAX_SIM, MAX_SIM_COSINE, MAX_SIM_IP, MAX_SIM_L2 (float vectors); MAX_SIM_HAMMING, MAX_SIM_JACCARD (binary vectors) |
| **Vector types** | FLOAT_VECTOR, BinaryVector, Float16, BFloat16, Int8 |

Under an element-level metric (L2, IP, COSINE, and the binary metrics), the same flattened vectors are passed without offsets, every element is indexed as an ordinary vector, and the index serves element-level search. This holds whether or not the sub-field is element-nullable; for an element-nullable sub-field the build also receives the element validity. When autoindex picks the metric of a sub-field that is not element-nullable, it maps its default element-level metric to the MAX_SIM counterpart. An element-nullable sub-field accepts only element-level metrics; MAX_SIM-family metrics, emb-list indexes and EmbeddingList search on it are rejected. See [element-level null](./20260709-element-level-null.md#vector-sub-fields) for the element id mapping.

### Scalar Index (Nested Index)

Scalar indexes on Struct sub-fields use **nested** semantics: each array element is indexed as an independent document, preserving positional information. This is the foundation for both `element_filter` and `Match Family` operations.

```
==== milvus format ====
row0:
  element[0]: { "color": "Red",  "size": "L" }
  element[1]: { "color": "Blue", "size": "M" }

row1:
  element[0]: { "color": "Blue",   "size": "L" }
  element[1]: { "color": "Yellow", "size": "XS" }
  element[2]: { "color": "Blue",   "size": "LL" }

==== nested index ====
doc 0: {"color": "Red",    "size": "L"}    <- row0, element[0]
doc 1: {"color": "Blue",   "size": "M"}    <- row0, element[1]
doc 2: {"color": "Blue",   "size": "L"}    <- row1, element[0]
doc 3: {"color": "Yellow", "size": "XS"}   <- row1, element[1]
doc 4: {"color": "Blue",   "size": "LL"}   <- row1, element[2]

offsets: [0, 2, 5]  (row0 has 2 elements, row1 has 3 elements)
```

The offset array maps element IDs back to row IDs at query time.

### Element Filter

`element_filter` filters Struct arrays at the granularity of individual array elements. `$[subFieldName]` references a sub-field of the current element. It can be combined with row-level filter conditions:

```python
filter = 'price > 100 && element_filter(clips, $[tag] == "sports" && $[score] > 0.8)'
```

**Constraint:** `element_filter` may appear at most once per filter expression and must be the last operand.

An element-level query returns, for each row, the positions of its matched elements: REST adds `"offset": [..]` to each row, and the Go SDK sets `ResultSet.QueryElementOffsets`. Rows are not expanded. Each hit of an element-level search carries the position of the matched element in its row: REST `"offset"`, Go SDK `ResultSet.ElementOffsets`. Both apply to every struct field, element-nullable or not; see [Client APIs](./20260709-element-level-null.md#client-apis).

### Match Family

A set of operators that apply a predicate to each element of an array and quantify the number of matches to determine whether the row passes. For Struct arrays, all sub-field conditions in the predicate must be satisfied by **the same element** (nested semantics).

| Operator | Semantics |
|----------|-----------|
| `MATCH_ANY(field, pred)` | At least one element matches |
| `MATCH_ALL(field, pred)` | All elements match |
| `MATCH_LEAST(field, pred, count=N)` | At least N elements match |
| `MATCH_MOST(field, pred, count=N)` | At most N elements match |
| `MATCH_EXACT(field, pred, count=N)` | Exactly N elements match |

```python
# Row 0: [{Red, L}, {Blue, M}] -> match (Red and L on the same element)
# Row 1: [{Blue, L}, {Red, LL}] -> no match (Red and L on different elements)
MATCH_ANY(structA, ($[color] == "Red") && $[size] == "L")
```

Implementation reuses the element-level filtering mechanism: evaluate the predicate at element-level, then aggregate per-doc bit patterns to apply the quantifier semantics (any/all/least/most/exact), producing a final doc-level result.

Null semantics of element-nullable sub-fields in row-level filters, `element_filter` and `MATCH_*` are described in [element-level null](./20260709-element-level-null.md#query-and-index).

### Nested Array Sub-fields in Filters

A nested scalar sub-field `tags`, stored as `Array<Array<T>>`, holds one `Array<T>` value per struct element.

- Row level, `s[i][tags]` is that `Array<T>` value. It supports `==` and `!=` with an array literal (not a template value), `array_contains`, `array_contains_any`, `array_contains_all` and `array_length`. An out-of-range `i` or a null inner array is UNKNOWN. Scalar operators (`<`, `in`, `like`, arithmetic, and others) on it are rejected.
- Element level, inside `MATCH_*` or `element_filter`, `$[tags]` is the same value for the current element. It supports `array_contains*`, `array_length` and `IS NULL` / `IS NOT NULL`; comparison operators, `in` and `like` on it are rejected.
- `array_contains*` on the whole sub-field (`s[tags]`) is rejected with a hint to rewrite it as `MATCH_ANY(s, array_contains($[tags], ...))`. `==` and `!=` on the whole sub-field are rejected as well.
- Not supported yet: a subscript into the inner array (`$[tags][j]`; the grammar has no such form) and an any-element `like` on `$[tags]`.

## Limitations

- Struct can only be used as the element type of `ARRAY`, not as a standalone field
- Sub-fields cannot be Struct or JSON; scalar Array sub-fields are supported, including one nested scalar Array level
- Sub-fields cannot set row-level nullable independently; they inherit the Struct field's row nullable value, while Array and ArrayOfVector sub-fields may use `element_nullable`
- Struct objects within an array cannot be null
- All sub-fields of a struct share one `max_capacity`, which must be in `(0, proxy.maxArrayCapacity]`; for a nested Array sub-field it is set on the root of its `type_schema`
- Setting `enable_match` or `enable_analyzer` to true is rejected on sub-fields, including on every level of a nested Array `type_schema`, because text indexes are built only for top-level fields
- `alter_collection_field` on a struct field or a sub-field accepts only `mmap.enabled`, `field.description` and `warmup`
