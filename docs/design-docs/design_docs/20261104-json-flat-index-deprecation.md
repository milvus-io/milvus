# JSON flat index deprecation

- Remove physical JSON flat indexing on master and 3.0. JSON flat means an authoritative schema identifies the field as JSON and its index has `json_cast_type=JSON`, including field roots, subtrees and dynamic fields. Cast parameters alone are insufficient because ordinary scalar indexes may carry ignored JSON extras. Typed JSON path indexes, JSON key statistics/shredding and vector FLAT remain supported.
- Retain collection-level index definitions with their existing IDs, names, fields, paths and parameters. Create and repeated create requests return success with a deprecation hint; no new per-segment index record, build task or index artifact is produced.
- Preserve existing SDK wait behavior through server responses: describe/state report `Finished`; progress/statistics report `indexed_rows=total_rows` and `pending_index_rows=0`. Completion means the request requires no physical build. A genuinely missing or dropped index remains missing, and normal name/conflict validation still applies.
- Public describe/list/drop continue to operate on logical definitions. Internal build/load/readiness consumers exclude JSON flat definitions and historical physical artifacts. API completion must never be interpreted as evidence that a loadable artifact exists.
- Do not create or dispatch new flat builds. Recover historical pending tasks only for retirement: cancel any assigned worker before deleting an artifact-free task from the catalog and in-memory maps, then remove it from scheduling. Retry cancellation or catalog failures, and ignore late publication. An older DataCoord recreates missing segment builds from the retained collection definition after downgrade, with fresh BuildIDs. Existing completed artifacts and any record still owning files remain intact. Terminal `Finished` and `Failed` records are not recovered or retired, including those without files. Unreported worker uploads remain subject to existing orphan-file GC and snapshot protections. Import, external refresh and compaction readiness must not wait for flat indexes.
- QueryNode upgrades stop loading flat indexes, including reopen and lazy-load paths. Queries use available typed path indexes, then shredding or raw JSON as applicable; NULL, missing-path, array and NOT semantics must remain correct.
- Snapshot restore may retain logical flat definitions, while new snapshot export/copy requests exclude their physical artifacts. A pre-upgrade copy may already have published flat files in its target manifest: result synchronization retains every verified artifact's ownership record (or segment summary), including flat builds. Physical-load filtering remains separate. This prevents orphan GC from deleting files that manifest recovery can later expose. Other data and indexes continue to restore normally.
- Historical manifest backfill excludes confirmed flat artifacts and retains their original etcd rows and file ownership. Ambiguous JSON-cast definitions wait for local schema visibility; nested fields use the same lookup as build admission and metadata readers. A missing field alone is not deletion evidence: the existing field-drop callback cascades index deletion, after which backfill leaves the durable record to ordinary GC. No RPC lookup or new lifecycle state is introduced.
- Rollback restores all retained manifest-resident records, including flat artifacts, unavailable schemas and missing/deleted definitions. It preserves BuildID, status and file references, copies v2 files to the supported v1 layout when necessary, and publishes the catalog rows and manifest retractions atomically. Readiness requires a subsequent scan with no remaining manifest-resident records; failed commits keep their original ownership and retry.
- Unknown candidates are not exposed as physical indexes or reported logically complete. Import/external-refresh readiness and inspector retries retain unresolved debt until schema visibility or explicit definition deletion resolves it. DataView compaction admission and clustering completion check every live index definition through its segment state: confirmed flat is logically Finished, while an unavailable schema is Unissued. Empty readiness targets retain the legacy segment-map gate for ordinary scalar collections; confirmed flat-only requirements need no segment records. Typed path indexes on the same JSON field still require their own Finished records.
- Build deduplication uses non-deleted current segment records by live index ID, independently of physical projection, so schema visibility changes at admission cannot hide and recreate an existing build.
- Delete flat-only C++ implementations, registration, expression special cases, Tantivy APIs and tests. Preserve shared typed-path/JSON-key-stats code and stable feature-bit numbering. Generate binding declarations through the existing generator.
- Preserve gRPC success reasons and include field/index-specific hints in REST batch and collection-creation responses. Older SDKs may discard successful reasons; server-side completion compatibility does not depend on clients reading a new flag.
- Historical logical definitions are not automatically marked deleted. Physical artifact reclamation is separate from this change and continues to obey existing snapshot/retention rules. No active unload procedure or new metadata/configuration flag is introduced.
- Validate logical creation/idempotency and real missing/drop behavior, completion without physical state, historical build/load suppression, restart, import/restore completion and query fallback. Run both branch implementations independently; retain the distinction between static traces, unit-test evidence and runtime/E2E evidence.

## Transitional compatibility window

This PR is an intermediate deprecation phase, not the permanent index model. During this phase, the server accepts existing JSON-flat parameters and preserves collection definitions so older clients keep working and a rollback to a flat-capable release can rebuild physical indexes. A later removal phase will reject these parameters and end this rollback compatibility. The exact release boundary is not selected by this PR; the classification and compatibility branches should be removed with that phase rather than becoming permanent requirements for new readers.

During an index-pool-first rolling upgrade, an older coordinator can still dispatch JSON flat builds. The worker recognizes these requests after resolving field metadata and effective index parameters, and returns `ErrServiceUnavailable` before creating a native builder. The scheduler reports `IndexState_Retry`, preserving the opportunity to build after worker rollback or to retire the pending task after coordinator upgrade. This is transitional unavailability of flat construction within the supported index-task protocol; generic native `Unsupported` errors retain their terminal handling. The old coordinator's retry/backoff behavior remains, without a new attempt limit. This does not repair already persisted terminal `Failed` records or create synthetic finished records.

A `Finished` segment record with no files is already valid for small segments and vector FLAT, and retaining such records would not add a new per-segment cost relative to the old implementation. It nevertheless fails this transition's rollback requirement: the old inspector deduplicates on the presence of a segment-index record and does not rebuild a finished record merely because its file list is empty. Creating synthetic finished records for new segments, or converting pending flat tasks to that state, would prevent automatic physical flat rebuilding after rollback. Therefore this phase creates no new flat segment records and deletes only artifact-free unfinished tasks after cancellation, while preserving their collection definition and historical artifact ownership. The additional classification logic is the temporary cost of retaining that rollback behavior while stopping physical flat indexing.

Query execution changes from the retired flat path to applicable typed path indexes, JSON stats/shredding, or raw JSON. The digit-leading object-key regression exposed by this fallback is fixed: Unary stats uses the complete escaped JSON pointer, while integer path components retain their existing raw-data array traversal. Other existing JSON stats/raw limitations are not fixed by this deprecation. #54022 reports potential filter-result differences for empty strings, duplicate keys and legacy invalid numeric values, based on code inspection rather than a runtime reproduction. #55154 reports stats-build retries for subnormal/out-of-range numbers, errors on digit-leading keys or array ordering, and errors or incorrect matches for nested-array comparisons. Except for digit-leading keys, these cases require separate fixes and are not covered by the basic upgrade/downgrade smoke test. Users with stable scalar paths can migrate to typed JSON path indexes with appropriate cast types; this is not a general workaround for every array or JSON-stats issue. Removing physical flat indexing does not itself establish identical results for all edge cases on these alternative paths.

Historical QueryView load configurations keep their exact index references and immutable versions. Explicit-ID metadata lookup resolves retained flat definitions; current load configuration publication still excludes them. QueryNode and StreamingNode physical consumers filter flat definitions using the exact field schema. Missing or mismatched references, including non-flat indexes, remain errors; compatibility does not turn arbitrary missing metadata into a raw-data fallback.
