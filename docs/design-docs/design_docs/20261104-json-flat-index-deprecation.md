# JSON flat index deprecation

- Remove physical JSON flat indexing on master and 3.0. JSON flat means an authoritative schema identifies the field as JSON and its index has `json_cast_type=JSON`, including field roots, subtrees and dynamic fields. Cast parameters alone are insufficient because ordinary scalar indexes may carry ignored JSON extras. Typed JSON path indexes, JSON key statistics/shredding and vector FLAT remain supported.
- Retain collection-level index definitions with their existing IDs, names, fields, paths and parameters. Create and repeated create requests return success with a deprecation hint; no new per-segment index record, build task or index artifact is produced.
- Preserve existing SDK wait behavior through server responses: describe/state report `Finished`; progress/statistics report `indexed_rows=total_rows` and `pending_index_rows=0`. Completion means the request requires no physical build. A genuinely missing or dropped index remains missing, and normal name/conflict validation still applies.
- Public describe/list/drop continue to operate on logical definitions. Internal build/load/readiness consumers exclude JSON flat definitions and historical physical artifacts. API completion must never be interpreted as evidence that a loadable artifact exists.
- Do not enqueue new builds or recover historical flat builds after restart. Retire pending/dispatched work and ignore late publication so old tasks cannot resurrect physical indexes. Import, external refresh and compaction readiness must not wait for flat indexes.
- QueryNode upgrades stop loading flat indexes, including reopen and lazy-load paths. Queries use available typed path indexes, then shredding or raw JSON as applicable; NULL, missing-path, array and NOT semantics must remain correct.
- Snapshot restore may retain logical flat definitions, but snapshot export/copy/result synchronization must exclude their physical artifacts. Other data and indexes continue to restore normally.
- Delete flat-only C++ implementations, registration, expression special cases, Tantivy APIs and tests. Preserve shared typed-path/JSON-key-stats code and stable feature-bit numbering. Generate binding declarations through the existing generator.
- Preserve gRPC success reasons and include field/index-specific hints in REST batch and collection-creation responses. Older SDKs may discard successful reasons; server-side completion compatibility does not depend on clients reading a new flag.
- Historical logical definitions are not automatically marked deleted. Physical artifact reclamation is separate from this change and continues to obey existing snapshot/retention rules. No active unload procedure or new metadata/configuration flag is introduced.
- Validate logical creation/idempotency and real missing/drop behavior, completion without physical state, historical build/load suppression, restart, import/restore completion and query fallback. Run both branch implementations independently; retain the distinction between static traces, unit-test evidence and runtime/E2E evidence.
