# ASYNC_LOAD 每组任务数量对照（2026-11-13）

## 结论

同一个分组队列实现，固定 16 个 worker 和 4096 条任务链，仅改变共享同一 load_seq 的任务链数：从每序号 4 条增加到 64 条，空任务吞吐从 89.8 万增加到 150.0 万次/秒；10 μs 任务从 77.0 万增加到 111.6 万次/秒。继续增大每组任务数量，吞吐基本持平。

计数表明，组内任务较少时会反复取空、重新发布组，生产者频繁争取全局调度锁。每序号 4 条的空任务场景，约 72.36% 的提交获取发布锁；每序号 64 条时降到约 0.39%。

这支持“原基准每组任务过少，使分组优化难以发挥”的判断。不能把吞吐提升描述成生产代码优化：本轮没有修改生产实现，而是改变了基准工作负载。总组数和组内任务数量在此实验中同时变化，没有完全独立地测量两者；从 128 组继续减少到 2 组时吞吐不再提高，则不支持总组数越少越快的简单结论。

## 控制条件

- 16 个 worker，4096 条独立自提交任务链，每次运行总计 1,048,576 个任务。每条链执行次数、业务工作量、HIGH/LOW 比例和 CPU 亲和性相同。
- HIGH 占 25%，LOW 占 75%。每个序号有 K 条链，实际分成 K/4 条 HIGH 链和 3K/4 条 LOW 链，对应两个 `(priority, load_seq)` 组。K 取 4、16、64、256、1024、4096。
- 只将基准中的序号赋值从 `1 + i / 4` 改为 `1 + i / K`。没有合并生产中的不同 load_seq，也没有改变队列比较规则。
- 吞吐用不插桩的临时基准二进制，随机交错各运行 5 次，取中位数。另用插桩二进制各运行 3 次统计计数；表中的锁比例来自该独立阶段，不将它的吞吐混入性能数据。
- 计数器是线程本地的，统计不增加共享锁或共享原子计数。记录每次提交、入队获取发布锁、实际 push_heap、出队预留和移除空组，以及成功预留时的组内未预留任务数、就绪堆大小。不读取时钟。

## 吞吐

单位：百万次任务执行/秒。组数只计加载任务的 `(priority, load_seq)` 组，不计线程池启动/退出使用的无序号组。

| 每个序号的链数 | HIGH / LOW 每组链数 | 总组数 | 空任务 | 工作 10 μs |
| ---: | ---: | ---: | ---: | ---: |
| 4 | 1 / 3 | 2048 | 0.898 | 0.770 |
| 16 | 4 / 12 | 512 | 1.399 | 0.959 |
| 64 | 16 / 48 | 128 | 1.500 | 1.116 |
| 256 | 64 / 192 | 32 | 1.477 | 1.115 |
| 1024 | 256 / 768 | 8 | 1.487 | 1.127 |
| 4096 | 1024 / 3072 | 2 | 1.480 | 1.114 |
| Folly + 元数据适配器对照 | 1 / 3 | 不按 seq 排序 | 3.338 | 1.186 |

这里的 Folly 对照包含元数据适配器，不能等同于完全不携带元数据的默认 Folly。该对照沿用 K=4，未遍历 K；它没有按 seq 分组的队列。5 次运行范围保存在 summary.json，主机上的其他负载没有隔离。

## 组发布与取空

计数比例为 3 次计数运行的总次数除以总提交任务数。每个场景共计 3,145,728 个任务。初始提交包含在计数里，随后每次再次提交也分别计数。

| 每序号链数 | 空任务：获取发布锁 | 空任务：实际发布组 | 空任务：拿锁后未发布 | 10 μs：获取发布锁 | 10 μs：实际发布组 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 4 | 72.36% | 53.67% | 18.68% | 77.73% | 63.66% |
| 16 | 10.32% | 5.81% | 4.51% | 42.61% | 30.03% |
| 64 | 0.39% | 0.38% | <0.01% | 5.75% | 4.04% |
| 256 | 0.24% | 0.23% | 0.01% | 0.09% | 0.07% |
| 1024 | 0.05% | 0.04% | 0.01% | 0.03% | 0.02% |
| 4096 | 0.01% | 0.01% | <0.01% | <0.01% | <0.01% |

K=4 的空任务场景中，约 25.82% 的入队发布锁获取没有执行入堆操作（18.68% / 72.36%）。生产者读取到组未就绪后，等待全局锁期间可能已经被其他生产者发布，或再次被消费者取空。因此存在具体的重复争锁成本，不只是堆比较次数多。

每次实际组发布最终都对应一次空组移除。每个计数运行都检查发布数等于移除数、提交数等于出队数等于总任务数。计数过滤了启动/退出的无序号组，并在基准自检完成后才启用，避免把自检计入任务统计。

| 每序号链数 | 空任务：预留前组内未预留任务数均值 | 空任务：预留时就绪堆组数均值 |
| ---: | ---: | ---: |
| 4 | 1.64 | 767.27 |
| 16 | 5.03 | 192.46 |
| 64 | 34.35 | 48.47 |
| 256 | 154.11 | 12.50 |
| 1024 | 632.96 | 3.50 |
| 4096 | 2548.57 | 1.25 |

第一列均值只计算组内尚未被消费者预留的任务，不包含已经取走或正在执行的任务。两种数量按成功出队事件加权，不是按墙上时间加权。

## 对后续实现的意义

1. 原来每 HIGH 组只有一条自提交链，容易形成“取走唯一任务→组变空→任务再次提交→重新发布组”的循环。组内积累足够任务后，入队大部分避开全局发布锁，性能明显改善。
2. 下一步可以研究如何减少多个生产者重复争取发布锁，但不能仅依据无操作次数推导吞吐收益。发布许可必须在组可见后发生，还要处理发布者延迟、消费者取空和其他生产者同时到达的情况。
3. 出队仍然每次都取得全局选择锁。即使只剩两个组、几乎没有重新发布，空任务吞吐仍约 148 万次/秒，低于本轮 Folly + 元数据对照的约 334 万。消除入队重复争锁不会消除全部差距。
4. 不因这组数据直接合并真实加载的不同 load_seq，也不直接改成 seq 低位 bucket；这会引入排序语义问题。应先观察真实 segment 加载时每组就绪任务数量，判断稀疏组是否常见。K=64 是本次 16 worker 基准进入吞吐平台的大致位置，不是通用配置建议。

## 验证与复现

70 次不插桩吞吐运行、36 次计数运行全部退出 0。每次运行都执行既有排序/生命周期自检，并检查每条链的完成次数；36 次计数运行额外检查提交/出队和发布/移除的计数守恒。未修改生产代码，生产源码与实验保存的快照逐字节一致。

[记录目录](benchmarks/async-load-group-density-20261113/) 包含原始 CSV、各线程计数日志、汇总、源码快照、插桩生成脚本和二进制校验和。环境继续使用 Xeon Gold 6338、此前的 16 CPU 亲和性、worker nice 19，GCC 12/C++20/-O3/-g1/-fno-omit-frame-pointer。编译按单个翻译单元依次进行，基准串行运行。

以下脚本从保存的 .cpp.txt 快照生成两个临时实现，在记录目录内构建并重跑；run.py 会覆盖 CSV 和计数日志。构建仍依赖本机 Conan 路径、worktree 头文件和 /tmp/load-seq-include，不是跨机器通用脚本。

```bash
python3 docs/design-docs/benchmarks/async-load-group-density-20261113/build.py
python3 docs/design-docs/benchmarks/async-load-group-density-20261113/run.py
python3 docs/design-docs/benchmarks/async-load-group-density-20261113/summarize.py
```

没有真实 segment load/reopen 或 I/O admission 验证。插桩会改变线程交错，因此它提供的是发布频率的近似证据；吞吐数据来自单独的不插桩运行。本轮没有重新抓 CPU profile，不能把进入平台后的全部开销都归因于出队锁。
