# ASYNC_LOAD 调度基准（2026-11-13）

## 结论

当前全局 mutex + 每任务堆的实现，在短任务和高并发下有明显吞吐回退，不建议仅凭排序正确性就合入。16 worker 的控制组表明，序号上下文适配器不是这些场景中主要的吞吐下降来源。尚未通过锁剖析区分互斥锁竞争、堆调整、任务移动及缓存访问各自的占比。

以下使用较长确认测试的 **5 次独立运行中位数**，没有选择最好的一次。

## 执行器吞吐

16 worker；每条任务链执行后重新提交自身，模拟恢复入队压力。每组 sequence 对应 4 条任务链；25% HIGH、75% LOW。初始全部任务就绪，随后任务链陆续结束，因此“任务链数”不是恒定队列深度。工作量为基于 steady_clock 的忙等目标时间；0 表示不添加业务工作。

单位：百万次任务执行/秒。

| 64 | 0 μs | 3.475 | 3.430 | 0.627 | 81.9% |

## 纯队列成本

16 个并发调用线程，每个线程反复取出一个 CPUTask，再放回一个 CPUTask。队列项数保持在 [初始深度−16, 初始深度]。任务的 RequestContext 预先创建，排除了每次创建上下文的成本；每次放回时更新序号上下文和优先级。一次操作是“出队＋入队”一对。

| 深度 | Folly 默认（百万对/秒） | Folly＋LifoSem（百万对/秒） | 当前堆（百万对/秒） | 默认 p99 | 当前堆 p99 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 64 | 4.282 | 4.161 | 0.607 | 11.08 μs | 88.81 μs |
| 4096 | 4.302 | 4.135 | 0.216 | 9.96 μs | 337.93 μs |

默认版本使用 ThrottledLifoSem；folly_lifo 控制组改用与当前堆相同的 LifoSem，仍保留 Folly 原来的并发 FIFO。这组对比说明，较大的差距不能只归因于信号量不同。纯队列测试按每 64 次操作采样一次延迟；表中 p99 是每次运行 p99 的中位数。

## 测试条件和验证

- Intel Xeon Gold 6338，128 逻辑 CPU / 64 物理核；限制在同一 NUMA 节点的 16 个物理核对应的逻辑 CPU，未使用它们的 SMT 兄弟核。亲和性是进程可用 CPU 集合，不是独占绑定；系统负载约 30–42。CPU 编号和源码、二进制 SHA256 见 environment.json。
- GCC 12、C++20、`-O3 -DNDEBUG -msse4.2`，无 sanitizer。Folly 是本机 Release 构建；实际加载的 libfolly 与构建缓存匹配。
- 所有 executor 变体使用当前 ASYNC_LOAD 的线程工厂（Linux nice 19）。纯队列线程是普通 std::thread，nice 0；不跨两种测试模式比较绝对吞吐。
- 基准直接包含当前 AsyncLoadExecutor.cpp，测量原实现的私有队列及适配器，没有复制重写队列算法，也没有改生产接口。全局 Milvus 池未初始化。
- broad sweep：1/4/16 并发，深度 64/4096/65536，4 轮交错随机顺序，第一轮丢弃；共 196 次。较短测试存在明显波动，最终主表采用延长确认测试。
- confirm：上述 7 个关键场景、每场景 3 个变体、5 轮交错随机顺序，共 105 次。每个零工作量场景执行 1,048,576 次；10 μs 场景执行 524,288 次；100 μs 场景执行 131,072 次。
- 每个进程开始前检查 HIGH/LOW、load_seq 和 FIFO ties 的出队顺序。纯队列结束检查元素数不变；执行器结束检查每条链的完成次数。构建成功；全部运行退出码为 0；301 条原始记录完整。
- executor_chain CSV 的 p50/p99 只采样后续重新提交到开始执行的延迟，每 16 次采样一次，排除第一次入队等待。它不包含晚序号组第一次获得执行机会的等待，也不是 load 完成延迟。堆可能改善早组的重入延迟，同时推迟晚组，不能用该列宣称整体尾延迟改善。
- 源码格式检查和 git diff --check 通过。
