# 9. 同一输入下的调度权重对照：1:1:1 与 32:8:1

本节直接回答：同一批输入负载下，调度权重从 1:1:1 改成 32:8:1 后，URGENT latency 如何变化。两版都是加权轮转，没有严格优先级版；与第 8 节的“严格优先级 vs 32:8:1”不是同一个对照。以下所有箭头均表示调度权重 1:1:1 → 32:8:1。

## 9.1 重点结果：固定输入 68 URGENT + 68 HIGH + 68 LOW

两边都提交同样的 204 个等成本 segment，提交顺序、window 数、CPU/I/O 参数和资源上限完全一致。这里输入数量比例一直是 1:1:1，改变的仅是 CPU 调度权重。响应时间从提交到完成，包含等待。

| 负载 | URGENT P50 ms | P50 变化 | URGENT P95 ms | P95 变化 | 整批 ms |
| --- | --- | --- | --- | --- | --- |
| CPU 较重 | 945.0 → 490.5 | -48.1% | 1708.8 → 819.2 | -52.1% | 1793.9 → 1801.2 |
| CPU / I/O 混合 | 251.9 → 242.2 | -3.9% | 392.7 → 400.4 | +1.9% | 408.0 → 416.1 |
| I/O 较重 | 440.9 → 492.8 | +11.8% | 854.0 → 855.8 | +0.2% | 892.7 → 913.8 |

CPU 较重时，URGENT 的 P50 为 945.0 → 490.5 ms，P95 为 1708.8 → 819.2 ms。这是同输入、同成本的权重对照，不是拿不同数量的 URGENT 比较。混合和 I/O 场景的结果单独列出，不把 CPU 场景的改善比例外推。

| 负载 | HIGH 响应 P50 ms | LOW 响应 P50 ms |
| --- | --- | --- |
| CPU 较重 | 951.1 → 1000.6 | 954.4 → 1522.4 |
| CPU / I/O 混合 | 268.4 → 246.9 | 253.8 → 262.2 |
| I/O 较重 | 495.3 → 487.4 | 457.1 → 484.6 |

更高的 URGENT 份额来自重新分配执行机会，不是减少工作量。HIGH/LOW 的延迟也必须同时看；整个批次的耗时接近，不代表每一类任务的延迟接近。

## 9.2 如何保证只比较权重

从同一版 AsyncLoadExecutor.cpp 构建两个实验二进制，代码差异仅为 kWeights{1,1,1} 与 kWeights{32,8,1}。生产 worktree 保持 32:8:1，没有为了实验改动生产配置或接入 Search。两版共用同一个已经修正屏障生命周期的协程负载驱动、资源限流器对象和依赖库。

配额功能检查使用单 worker 的持续 co_await 重新排队负载：41,000 次工作在 1:1:1 下分成 13,667 / 13,667 / 13,666 次，在 32:8:1 下分成 32,000 / 8,000 / 1,000 次；两版 checksum 一致。份额计数是任务取出机会，不是 CPU 时间，也不是 segment 数。

沿用第 8 节的 8 个输入场景与 3 种 CPU/I/O 配置，每组两版各 5 轮，随机交错，共 240 次新运行。没有把此前不同轮次的结果拼入本节。每对使用相同 plan.tsv，包括优先级、CPU 成本倍数、计划到达时刻；每个 segment 为 4 字段 × 16 window，16 worker。常规资源名额为 64，资源充足诊断为 16384。突发为 160 HIGH + 40 LOW 先开始，20 ms 后提交 5 URGENT，逐轮确认后台仍有任务未完成。

P50/P95 使用最近秩法，排序后取第 ceil(p×N) 个值；先在每轮对应级别内计算，再取 5 轮中位数。100:1:1 输入中的 HIGH/LOW 各仅 2 个样本，其他少量级别可能仅 5 个，P95 实际为该轮最大值。共享主机上每组 5 轮，不据此给出生产置信区间或延迟上限。

## 9.4 解释与验证边界

只有在多个优先级同时存在就绪任务时，配额才限制它们之间的选择。某一级为空，其他级立即借用机会；所以不能把“份额从约 33% 到 78%”直接换算成固定的延迟倍数。成本不等时，一个长 CPU 片段仍只计一次，运行中的任务不可抢占。

资源申请仍统一采用原有 HIGH + load_seq 策略，CPU 的 URGENT 并不会自动变成资源等待中的 URGENT。I/O 与资源等待可能占主导，因此本节既报告 CPU 密集条件下的收益，也保留混合、I/O、突发和成本不等条件的全部结果。真实 Search 尚未接入，不把合成 segment 的响应时间称为 Search latency。

240 次正式运行全部正常退出，120 对逐 segment 的优先级、工作量和 checksum 一致；校验了时间戳顺序与全部资源归还。两种权重的功能检查也通过。未改动生产代码，未重跑完整 Milvus 集成构建；真实存储、开放环持续到达、生产 Search 和长期尾延迟仍未验证。
