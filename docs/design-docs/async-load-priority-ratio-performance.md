# 8. 32:8:1 调度：不同提交比例与突发竞争补测

第 1—7 节保留此前严格优先级与信号量替换的历史结果。本节记录后续 CPU 加权调度：URGENT:HIGH:LOW 每轮分别获得 32、8、1 次取任务机会，空级跳过，同级仍按 load_seq 和 FIFO 排序。这里的权重是任务取出次数，不是 segment 数、CPU 时间或提交流量比例；一个 segment 会生成多个协程任务，实际挂起与恢复次数也会受竞争影响。

本轮只补充测试，没有继续修改生产调度器。严格版与加权版使用同一三级队列实现及 ThrottledLifoSem，只改变优先级选择策略；Folly 线程池和协程机制不变。资源申请在两版中统一使用原有 HIGH + load_seq 策略，尚未为 Search 接入端到端 URGENT。

本轮结论：不同提交比例的取舍明显不同。CPU 等成本场景整批基本持平，但 32:8:1 输入下 HIGH/LOW 提前、URGENT 变慢；100:1:1 输入下少量 HIGH/LOW 也能提前完成。不能把 1:1:1 或全部 HIGH 的表现外推到所有流量构成。

需要特别注意成本不等和资源竞争：HIGH 成本 ×4 时，URGENT 的 CPU 场景响应 P50 为 400.6 → 702.0 ms；I/O 突发中，加权版 URGENT 响应 P50 在 64 个资源名额下为 875.7 ms，名额充足的诊断对照为 22.1 ms。这些结果不支持只靠任务次数权重保证 Search 延迟。

前一轮全部 HIGH 的同轮对照中，加权版相对严格版的整批耗时变化为 CPU -0.5%、混合 -0.2%、I/O +1.8%、单 segment -0.6%，未观察到严重额外开销；这些是前一轮数据，不与本节不同比例结果合并统计。此前持续 co_await 重新排队的单 worker 测试也验证了 41000 次工作分为 32000/8000/1000；本节进一步改变输入构成。

每个 segment 为 4 字段 × 每字段 16 个 window；16 个 CPU worker，通常 64 个名额，每 window 记账 1 MiB。CPU / 混合 / I/O 场景分别使用（模拟 I/O 延迟，CPU 运算次数）=(0 ms,800000)、(1 ms,100000)、(4 ms,10000)。×4 只扩大单 window 的 CPU 运算次数，不扩大 window 数、I/O 延迟或记账内存。

所有普通场景批量提交，并按固定随机种子打散优先级在提交顺序中的位置；配对的两版本使用完全相同的计划和 checksum。突发场景先提交 160 HIGH + 40 LOW，再于 20 ms 提交 5 URGENT；每次都检查 URGENT 到来时仍有后台 segment 未完成。资源充足对照把名额设为 16384，大于全部 13120 个 window，仅用于隔离资源申请竞争；这是合成记账额度，不是生产配置建议。

8 个场景 × 3 种负载 × 2 个版本 × 5 轮，共 240 次正式运行。两版本随机交错、绑定同一 NUMA 的 16 个物理核。每个场景单独做前后配对，不把 204 和 205 个 segment 的整批耗时直接跨场景比较。所有性能表均为“严格 → 加权”，单位 ms。响应时间从提交到完成，active 从首次执行到完成；P50/P95 使用最近秩法：排序后取第 ceil(p×N) 个值，先在每轮对应优先级内计算，再取 5 轮中位数。

100:1:1 的 HIGH/LOW 每轮仅各 2 个样本，32:8:1 的 LOW、1:32:8 的 URGENT 每轮仅 5 个样本，其 P95 实际等于该轮最大值，不能视为稳定的生产尾延迟估计。首次执行等待和资源 await 的最大值表使用 5 轮中最坏观察值，不是理论上限。

## 8.4 结果分析与适用边界

提交数量比例也为 32:8:1，CPU 场景的 URGENT/HIGH/LOW 响应 P50 分别为 779.1 → 973.2、1600.0 → 946.1、1788.5 → 1061.4 ms，整批变化 +0.2%。因此不能只用 1:1:1 的结果代表其他流量配比，也不能把固定调度份额理解为整个批次始终按该比例使用 CPU。某一级完成后，其余级会使用空出的执行机会。

URGENT 占绝大多数的 100:1:1，CPU 场景的 URGENT/HIGH/LOW 响应 P50 分别为 946.3 → 984.1、1774.1 → 168.4、1790.7 → 398.7 ms，整批变化 +0.3%。因此不能只用 1:1:1 的结果代表其他流量配比，也不能把固定调度份额理解为整个批次始终按该比例使用 CPU。某一级完成后，其余级会使用空出的执行机会。

少量 URGENT 的 1:32:8，CPU 场景的 URGENT/HIGH/LOW 响应 P50 分别为 141.7 → 115.1、819.7 → 906.2、1640.1 → 1638.1 ms，整批变化 +0.2%。因此不能只用 1:1:1 的结果代表其他流量配比，也不能把固定调度份额理解为整个批次始终按该比例使用 CPU。某一级完成后，其余级会使用空出的执行机会。

HIGH 单 window CPU 成本 ×4 的场景，URGENT 响应 P50 从 400.6 ms 增至 702.0 ms（+75.2%）。5 对样本均为加权版更慢。这是需要单独评估的延迟代价，不能被整批耗时接近所掩盖。

也并非所有整批耗时都持平：32:8:1 输入的混合场景整批为 397.1 → 427.7 ms（+7.7%），5 对中有 4 对加权版更慢，原始样本波动较大。保留该结果，不将其直接归为噪声，也不凭 5 轮断言稳定回归。

成本不等时，32:8:1 只约束取任务次数。一个 ×4 的 CPU 片段仍只占一个名额，且正在运行的片段不可抢占；因此任务数比例不能保证 CPU 时间比例。×4 场景只与自身的严格版比较，不能把工作量增加导致的耗时变化误算成调度回归。

突发测试同时覆盖首次执行和完成响应；资源名额充足对照用于观察资源限制的影响，但它也改变了总并发度，因此两组差值不能精确拆成某一种等待的独立成本。生产上仍需同时检查 CPU、资源申请和 I/O 路径，不能仅凭 CPU 加权队列承诺 Search 的延迟上限。

这些是有限批次排队和一次突发，不是长期开放环 QPS 测试；本轮也没有比较其他权重组合。因此它能验证 32:8:1 在不同输入构成下的行为和取舍，不能证明该权重最优。共享机器每组 5 轮，只报告测量值，不把几个百分点的变化直接归因为稳定收益或回归。

## 8.5 校验、修正与原始数据

240 次正式运行全部退出 0；逐 segment 校验了优先级、CPU 成本倍数、window 数、提交/开始/完成时间顺序，配对版本 checksum 一致，并检查资源全部归还。本轮未改变生产代码，因此没有重跑不相关的完整 Milvus 测试；真实 Segment::Load、对象存储、Search 生产调用链及长期饥饿边界仍未验证。

最初用 100 ms 触发 URGENT，其中资源充足的 I/O 对照有一轮后台已在 99.8 ms 完成。该条件不满足竞争测试，所有 100 ms 突发样本单独归档，突发场景统一改为 20 ms 后重测；58 次未受该参数影响的非突发运行保留，其余补齐到 240 次。正式数据逐轮验证了真实重叠，未选择性保留“效果好”的样本。

上一轮极短负载的退出异常已定位到测试启动屏障按引用捕获的生命周期问题，修正后重新跑过 150 次基准并正常退出。本轮沿用修正后的屏障。此前第 6 节记录的历史异常不应被理解为本轮仍在复现，也不据此宣称所有其他退出问题均已解决。
