# Paimon L3 CI and phase control

The standard test module is
`milvus_client/test_milvus_client_external_table_paimon_l3.py`. It implements
PAI-L3-13 and its before-apply and wait-disabled controls. All three cases use
`CaseLabel.L3` plus `paimon_refresh_serial`; the option is registered in root
conftest. Ordinary L0/L1/L2 CI does not select them.

## Dedicated CI entry

The CI job owns an empty standalone deployment built with the optional hooks,
its MinIO bucket, a scoped Kubernetes identity, and the profile below. Prepare
Python using the existing `tests/scripts/python-env.sh` and install the existing
Python-client requirements, as ordinary E2E CI does. The driver additionally
needs `kubectl` in this dedicated job; ordinary Paimon cases need no operator tools.

From the repository root with the prepared E2E venv active:

```sh
PAIMON_L3_PROFILE=/mounted/ci-profile.json \
tests/scripts/ci_paimon_external_l3.sh \
  --host paimon-l3-milvus.ci-namespace.svc.cluster.local --port 19530 \
  --minio_host paimon-l3-minio.ci-namespace.svc.cluster.local \
  --minio_bucket dedicated-bucket --junitxml=/artifacts/paimon-l3.xml
```

The entry retains standard connection/MinIO/JUnit options and fixes selection to
this module, `--tags L3`, and `-n 0`. Root conftest rejects parallel or mixed L3
selection before any fixture runs. A selected execution with no profile fails;
collection-only can inspect its three cases without a deployment.

Service-mode CI profile (replace values with the job's actual deployment):

```json
{
  "protocol": 1,
  "dedicated": true,
  "milvus_uri": "http://paimon-l3-milvus.ci-namespace.svc.cluster.local:19530",
  "control_command": ["/path/to/venv/bin/python", "/checkout/tests/python_client/scripts/paimon/k8s_phase_driver.py"],
  "target": {
    "access_mode": "service",
    "cluster": "https://kubernetes.default.svc",
    "namespace": "ci-namespace",
    "deployment": "paimon-l3",
    "milvus_service": "paimon-l3-milvus",
    "etcd_service": "paimon-l3-etcd",
    "image": "registry/milvus:completed-hook-build",
    "etcd_endpoint": "http://paimon-l3-etcd.ci-namespace.svc.cluster.local:2379",
    "etcd_root_prefix": "dedicated-root"
  }
}
```

Service mode supports standard Helm or Operator standalone services. Set the
actual Service names explicitly: Helm can name the Milvus Service exactly like
the release when its release name already contains `milvus`. It does not
call `milvus-dev-cli` or read a Milvus CR. It verifies service DNS/ports, endpoint
Pod UID/IP, image/readiness and the selected etcd root's rootcoord/datacoord sessions
before acquiring its CAS lease. A unique completed baseline job is checked again
before configuration changes. The deployment must have only the default database,
no pre-existing collections and no active gate.

Omitting `kubeconfig` selects the runner's projected service account. The driver
verifies the in-cluster API address and writes a mode-0600 kubeconfig containing a
`tokenFile` reference, never the token bytes. Alternatively set `target.kubeconfig`
to a mounted, explicitly scoped kubeconfig. The identity needs namespace-scoped
get/list of pods/services/endpoints and exec on the selected standalone pod; it
needs no host-cluster access or deployment mutation permissions. Config changes
use the explicitly selected dedicated etcd endpoint/root. Set `MILVUS_L3_TOKEN`
when the Milvus token differs from the default test token.

For local Cell execution, use `access_mode: "cell"` (also the backward-compatible
default), an explicit personal kubeconfig and Cell external Milvus/etcd URLs.
This mode additionally checks `milvus-dev-cli deploy status` against the profile.
Keep those operator credentials out of the ordinary remote PySDK runner.

## Build the test-hook deployment

Apply `scripts/paimon/l3_test_hooks.patch` to an isolated checkout at
`4f95cb61d849bd4ecb03fa1f641179825a58b05d`. This patch is only for the dedicated
L3 test image. The ordinary L0–L2 image is the unmodified PR build.

```sh
git apply /absolute/path/to/tests/python_client/scripts/paimon/l3_test_hooks.patch
go test -tags dynamic,test '-gcflags=all=-N -l' -count=1 ./internal/util/paimone2ehook
milvus-dev-cli build local . -b master --allow-dirty
milvus-dev-cli deploy create <completed-build-id> --name paimon-l3 --cu 1 \
  --config dataCoord.externalCollection.refreshWaitForIndex=false \
  --config dataCoord.externalCollectionJobTimeout=600 \
  --config dataCoord.externalCollectionCheckInterval=1
```

A CI deployment owner may build/deploy through its normal tooling instead. The
profile must identify that actual hook image and its own endpoints/root. This
repository supplies the executable CI entry and backend; provisioning or scheduling
an external Jenkins L3 job remains a pipeline-owner integration step.

## Evidence and restoration

The index gate selects the actual collection, field and index. It is armed only
after S1 has a single, fully built ANN index. Atomic event files contain the
actual build/segment/field/index IDs and manifest path. While blocked, the driver
binds each event to a live S2 segment's manifest. `target_snapshot_id` is the
requested pin; `task_spec_snapshot_id` is the actual task's collection spec,
which may predate publication. These are recorded separately. A configured
snapshot copied into an event is never used as proof of task lineage.

For post-apply timeout, actual job metadata must show `segments_applied=true`, a
nonzero index wait marker, and an observation of that marker while InProgress.
After Failed, S2 must serve before and after reload. Unblocking must let the ANN
build complete before another refresh is submitted. The original job stays Failed;
same-snapshot retry must not duplicate live segment IDs/rows or logical data.

Before-apply timeout requires an observed apply gate and `segments_applied=false`;
zero wait time alone is insufficient. With waiting disabled, Completed must occur
while the index gate is active and pending index rows remain positive. All three
cases finish with full GT, actual ANN, recall/distance and raw-output checks.

The driver confirms wait/timeout through the pod's runtime config endpoint. It
persists original etcd overrides and recovery state before mutations. Finalizers
remove lease-owned gates, restore absent/present overrides exactly, confirm runtime
values and RPC health, and release the CAS lease. Configuration restoration does
not depend on constructing a working Milvus RPC client first.

State lives under `tempfile.gettempdir()/milvus-paimon-l3/<lease>/state.json`;
the observer stops after 600 seconds or a `stop` file. If the test process is
interrupted, replay `restore` on the same workstation using that state:

```python
import json
import subprocess
from pathlib import Path

state_path = Path("/actual/temp/directory/milvus-paimon-l3/<lease>/state.json")
state = json.loads(state_path.read_text())
request = {
    "protocol": 1,
    "lease": state_path.parent.name,
    "action": "restore",
    "target": state["target"],
    "milvus_uri": state["uri"],
}
subprocess.run(
    ["/path/to/python3", "/path/to/scripts/paimon/k8s_phase_driver.py"],
    input=json.dumps(request), text=True, check=True,
)
```

The protocol uses argv without a shell and one JSON stdin/stdout exchange per
action (`prepare`, `arm`, `inspect`, `unblock`, `restore`), each bounded to 60 seconds.
Gate staging filenames include the current lease (`.writing-<lease>`), so restore
can remove even a truncated write. Legacy `.writing` files are removed only when
their JSON identifies the current lease; files belonging to another lease remain
untouched. Cleanup tolerates a delayed rename completing between listing and
deletion. The control lease is released only after gates are cleared, original
configuration is effective and the target passes its health/version checks.
Missing/inconsistent evidence fails the experiment. Remaining L3-01–12 profiles
are listed as pending in the implementation report; three timeout controls do
not establish chaos, upgrade, real-cloud, performance or 24-hour stability coverage.
