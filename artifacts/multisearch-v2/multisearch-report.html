Milvus engineering prototype · 31 October 2026

MultiSearch through the existing Milvus service

A native Python method and gRPC API that package independent searches across databases and collections into one call, with bounded dispatch through the existing Proxy Search path.

What this experiment demonstrates

The corrected implementation works over native gRPC on standalone Milvus. Under the two-CPU contention workload, MultiSearch achieved +8.2% logical throughput versus stock v3.0.5, with group p99 changing -5.3% and ordinary-Search probe p99 changing -7.1%. The modified ordinary Search path showed a +3.3% group-p99 increase and -0.4% throughput change, which remains a review caveat. Observed CPU utilization was 97.0% for stock and 97.0% for MultiSearch.

These are measurements of this workload, not a general latency or production-readiness guarantee. The Kubernetes evidence and remaining limits appear below.

1. The product contract

A consultation may need searches in multiple medical collections, each with its own vector dimension, metric, filter, output fields and topK. MultiSearch transports a list of those independent requests. Every item includes its own database and collection. Results stay separate and retain input order; there is no score fusion or cross-collection atomic snapshot.

client.multi_search([
    {"id": "papers", "db_name": "literature", "collection_name": "papers",
     "data": [paper_vector], "anns_field": "embedding", "limit": 10},
    {"id": "guidelines", "db_name": "clinical", "collection_name": "guidelines",
     "data": [guideline_vector], "anns_field": "vector", "limit": 3},
], max_concurrent_searches=8, timeout=5)

This extends the actual MilvusClient, GrpcHandler and MilvusService. The public RPC is /milvus.proto.milvus.MilvusService/MultiSearch. It uses the existing authenticated client channel. The protocol and SDK changes are provided as companion patches to their actual repositories; they are unpublished dependencies.

Transport batching reduces client-to-Proxy RPC count, not the underlying search work. Under an illustrative independent 3% per-RPC failure model, 100 calls have a 95.2% probability of at least one failure. One batched call has one transport exposure, but loses all its results if that call fails. Real PSC failures can be correlated; this prototype does not establish a 3% production question failure rate or validate any GCP SLA claim.

2. Why the wait does not consume a parent search worker

Python multi_search()
↓ one existing-service RPC
Proxy envelope admission + bounded dispatcher goroutines
↓ each item, independent DB and parameters
Ordinary Search entry chain: authentication · RBAC · quota · hooks
↓
Server.Search → Proxy.Search → ordinary DQL queue → QueryNode
↓
Ordered independent outcomes → one response

The concern about tying up threads is valid if the parent is put in the same finite worker pool as its children: all pool slots could wait for children that cannot run. Here, the parent stays outside the DQL pool. WaitGroup.Wait() and channel receives park Go goroutines instead of spinning or reserving an OS thread. The ordinary Search tasks still occupy their normal scheduler slots while executing. Waiting retains request/result state, and scheduling, serialization, allocation and leaf computation still cost CPU.

Current HybridSearch converts one database/collection request into a SearchRequest with SubReqs, then enqueues one search task and performs collection-local execution/reduction. It is a useful example of waiting for search completion, but its shared collection and ranking semantics do not provide independent cross-database dispatch. MultiSearch reuses the ordinary Search path separately for each item.

func (tc *TaskCondition) WaitToFinish() error {

Actual dispatcher implementation

The code below is extracted from the prototype. The semaphore is shared by all batches on this Proxy. The worker count is bounded per batch. The parent waits outside the search scheduler.

parallelism := e.limits.Parallelism
	if requested := req.GetMaxConcurrentSearches(); requested > 0 {
		parallelism = min(parallelism, int(requested))
	}
	// The RPC handler and these bounded workers stay outside the DQL pool.
	for range min(parallelism, len(req.Items)) {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for ctx.Err() == nil {
				i := int(next.Add(1) - 1)
				if i >= len(req.Items) {
					return
				}
				select {
				case e.active <- struct{}{}:
				case <-ctx.Done():
					return
				}
				if ctx.Err() != nil {
					<-e.active
					return
				}
				item := req.Items[i]
				// Search and entry interceptors may mutate the request. Never share
				// caller-owned request pointers between workers (or retry attempts).
				search := proto.Clone(item.Search).(*milvuspb.SearchRequest)
				result, err := e.search(ctx, search)
				<-e.active
				outcome := &milvuspb.SearchOutcome{Id: item.Id, Result: result}
				if err != nil {
					s := status.Convert(err)
					outcome.Result = nil
					outcome.GrpcCode, outcome.GrpcMessage = int32(s.Code()), s.Message()
				} else if result == nil || result.Status == nil {
					outcome.Result = &milvuspb.SearchResults{Status: merr.Status(merr.WrapErrServiceInternalMsg("Search returned no result status"))}
				}
				// Reserve protobuf framing overhead as well as outcome bytes.
				if resultBytes.Add(int64(proto.Size(outcome)+16)) > int64(e.limits.MaxResponseBytes) {
					overflow.Store(true)
					cancel()
					return
				}
				out.Items[i] = outcome
			}
		}()
	}
	wg.Wait()

Actual integration with the ordinary Search entry

A Go method call does not automatically invoke gRPC interceptors. The callback explicitly re-enters the shared Search chain before calling the existing server method. Request cloning and independent mutable RPC statistics prevent sibling state sharing.

entry := proxyEntryInterceptor(limiter, getMetaCache)
	search := func(ctx context.Context, req *milvuspb.SearchRequest) (*milvuspb.SearchResults, error) {
		// Fork mutable stats; the access-log interceptor similarly allocates
		// an independent object. Identity, deadlines and tracing are inherited.
		ctx = metrics.WithIndependentRPCStats(ctx)
		resp, err := entry(ctx, req, &grpc.UnaryServerInfo{Server: s, FullMethod: milvuspb.MilvusService_Search_FullMethodName},
			func(ctx context.Context, req any) (any, error) {
				return s.Search(ctx, req.(*milvuspb.SearchRequest))
			})
		if err != nil {
			return nil, err
		}
		result, ok := resp.(*milvuspb.SearchResults)
		if !ok || result == nil {
			return &milvuspb.SearchResults{Status: merr.Status(merr.WrapErrServiceInternalMsg("Search entry returned an invalid response"))}, nil
		}
		return result, nil
	}

Actual Python RPC call and item preparation

def multi_search(self, searches, max_concurrent_searches=0, timeout=None, context=None):
        """Execute independent searches with one RPC and no whole-batch retry."""
        if not searches:
            raise ParamError(message="multi_search requires at least one search")
        if not isinstance(max_concurrent_searches, int) or not 0 <= max_concurrent_searches < 2**32:
            raise ParamError(message="max_concurrent_searches must be a uint32")
        request = milvus_types.MultiSearchRequest(max_concurrent_searches=max_concurrent_searches)
        decimals = []
        for i, source in enumerate(searches):
            args = dict(source)
            item_id = str(args.pop("id", i))
            child_context = args.pop("context", context)
            db_name = args.pop("db_name", child_context.get_db_name() if child_context else "")
            child_context = CallContext(db_name=db_name)
            decimals.append(args.get("round_decimal", -1))
            child = self._prepare_search_request(timeout=timeout, context=child_context, **args)
            child.db_name = db_name
            request.items.add(id=item_id, search=child)
        response = self._stub.MultiSearch(request, timeout=timeout, metadata=_api_level_md(context))
        check_status(response.status)

3. Concurrency controls and established precedent

Elasticsearch's established _msearch API batches independent searches, including searches targeting different indices. Its max_concurrent_searches bounds concurrent sub-searches; the documented default is max(1, data nodes × min(search thread-pool size, 10)). Its max_concurrent_shard_requests separately limits each sub-search's concurrent shard requests per node, defaulting to 5. These distinguish request-level and shard-level pressure. This is a mature API pattern, not evidence that Milvus automatically inherits Elasticsearch's performance or fairness properties.

These controls are not a reservation for ordinary Search, a per-tenant fair scheduler or a cluster-wide concurrency limit. The prototype adds no new shard-concurrency control. The capacity tests use 128 shared permits and 32 admitted batches so MultiSearch is not compared with an artificially smaller logical-inflight limit.

5. Performance methodology

All paths execute identical groups of eight logical searches. Search sends eight concurrent ordinary RPCs; MultiSearch sends one RPC with eight items. Latency measures the time to complete the whole group in both cases. Performance items use nq=1 and topK 5–8; loaded batches contain eight items. Fifty-item batches are tested functionally, not benchmarked here. A compiled Go client avoids measuring Python fan-out limitations as server performance. Requests are pre-built and use the same vectors, parameters and authorization.

Each four-core capacity condition runs twice with reversed variant order, after five seconds of warmup and for 30 seconds of measurement. Logical concurrency caps are 8, 64 and 128. Offered-load runs at 480 and 1,200 logical searches/s are reported separately. Two-core saturation conditions run twice for 45 seconds each. CPU means are normalized to the actual quota and cover the entire standalone process, including Proxy, QueryNode and background components; they do not isolate Proxy CPU cost. GOMAXPROCS remains 4 in both binaries during the two-core stress; this deliberately tests contention rather than a tuned two-core deployment.

The active standalone process is pinned to CPUs 64–67 (64–65 for saturation); the inactive instance remains alive on a separate cpuset. The client uses CPUs 32–39. Each container has a 16 GiB memory limit and bounded 4 GiB tmpfs data storage. The host is shared; CPU affinity does not reserve sibling hyperthreads or NUMA memory placement. This is an in-memory CPU/read benchmark, not a durable-storage, PSC or WAN experiment. Initial pause/resume runs were discarded after embedded-etcd leases expired.

An ordinary Search probe shares the server with each load. It attempts a request every 50 ms but waits for each response, so slow responses reduce its sampling rate. Its p99 is diagnostic, not a constant-arrival SLA measurement. Tables pool raw latency observations across repeats; throughput and CPU are means. No confidence intervals or statistical-significance claims are made.

7. Failure semantics and production follow-ups

  • Successful siblings survive individual item failures. Ordinary SearchResults and Status are preserved; transport errors retain code/message only. Full gRPC details and trailers are not retained.
  • The SDK does not automatically retry the entire batch. A lost envelope response can repeat successful work if an application retries it; selective retry policy needs an explicit design.
  • Envelope deadline/cancellation and aggregate response overflow fail the unary response. There is no partial-result streaming or resume token.
  • Permits bound active Search calls, not all backend work remaining after cancellation. Transient allocations can exceed the retained-response budget.
  • Large batches concentrate work on one Proxy. Tenant fairness, distributed balancing, larger batches, HNSW/other indexes, larger results, slower heterogeneous backends and long-duration saturation require additional testing. Kubernetes testing here is functional, not a cluster performance claim.
  • Private Cloud gateway/billing hooks, envelope byte accounting, hot configuration updates and broader SDK data types need production review. REST and AsyncMilvusClient are not implemented.
  • The protocol and PyMilvus patches need normal upstream releases and dependency pins. The build recipe uses released native libraries, not a full C++/Rust rebuild. The checked-in PGO profile is empty; exact release PGO provenance was not reconstructed.

8. Engineering assessment

The prototype demonstrates that independent multi-database searches can be added at the existing MilvusService/Proxy boundary without changing QueryNode execution or imposing common schemas and metrics. Bounded dispatch keeps the parent out of the DQL pool and preserves per-item authorization. The recorded CPU-contention measurements address the waiting/thread concern for this fixture; they do not eliminate the need for resource limits or establish fairness for arbitrary workloads.
