The idea is feasible at the Proxy boundary

The implemented API accepts a bag of complete, independent Search requests. Proxy applies the normal Search entry checks to each item, invokes its ordinary execution path, and returns separate results. The prototype successfully searched collections with different schemas, dimensions, metrics and topK values in one external RPC.

This directly resolves the schema/metric objection in the discussion: a unified cross-collection ranking would require compatible scores and a defined merge operation. MultiSearch does neither. Each item validates its own collection and performs its own normal shard-level reduction. There is no reduce across items and no atomic cross-collection snapshot.

Evidence supports proceeding to API design review. The implementation and end-to-end tests demonstrate that this orchestration can live in Proxy without changes to QueryNode, Segcore, indexes or WAL behavior. Production readiness, customer latency targets and PSC incident mitigation require additional validation.

The fan-out happens in process, into the existing Proxy Search entry path. No loopback network calls are introduced. The dispatcher has no knowledge of schemas, shards, indexes, or score merging. Each item keeps its own nq and quota accounting; packing collections together does not turn them into one larger-nq collection search. Vector and result payloads still have to cross the network.

Entry checks must run per item

Calling Proxy.Search directly would bypass network interceptors. This implementation refactors the existing Search entry chain into a shared function, then explicitly runs it for every item using Search's real method name and request type. That preserves database handling, collection RBAC, per-item quotas, hooks, access logging and ordinary standalone forwarding. The envelope has its own explicit authentication/access chain; it does not rely on permissive fallbacks for unknown request types.

Requests are cloned before dispatch. Mutable RPC statistics and access-log state are isolated per item; identity, deadline and trace ancestry are inherited. Cloud-only gateway and billing hooks are not available in this OSS environment and remain a release gate.

What batching changes about failures

Under the illustrative assumption of independent 3% failures per external RPC, the chance of at least one failure in a group is 1 − (1 − 0.03)n: 78.2% for 50 RPCs and 95.2% for 100. A single envelope has 3% exposure in that simplified model; two envelopes have 5.91%, and three have 8.73%.

These are model calculations, not measured PSC behavior. Real network failures may be correlated, and larger payloads or longer requests may change failure probability. A failed envelope affects all its items. Adaptive model search rounds still need separate calls. Internal search failures and total database work do not disappear.

Returning partial outcomes does not relax the application’s requirement that every required search succeed. It makes the failed subset visible. A client can later retry only failed items when it receives a usable response, subject to an overall deadline, backoff and a single retry owner. Losing the entire response can require replaying the bag and repeating successful work. This prototype deliberately adds no retry policy.

The code that demonstrates the design

These excerpts are extracted from the implemented files. The complete protocol and dispatcher are small enough to review directly; generated protobuf bindings and the existing Search engine provide the rest.

pkg/proto/multisearch.proto · actual prototype source
syntax = "proto3";
package milvus.proto.multisearch;

option go_package = "github.com/milvus-io/milvus/pkg/v3/proto/multisearchpb";

import "common.proto";
import "milvus.proto";

// Prototype extension on the public Proxy gRPC port. Items are independent
// ordinary searches, not a cross-collection ranking or snapshot operation.
service MultiSearchService {
  rpc MultiSearch(MultiSearchRequest) returns (MultiSearchResponse) {}
}

message SearchItem {
  string id = 1;
  milvus.SearchRequest search = 2;
}

message MultiSearchRequest {
  string db_name = 1;
  repeated SearchItem items = 2;
}

message SearchOutcome {
  string id = 1;
  // Present for ordinary Milvus outcomes, including non-success Status.
  milvus.SearchResults result = 2;
  // Transport errors from the ordinary Search entry chain remain distinct
  // from Milvus Status. Zero means OK; nonzero means result is absent.
  int32 grpc_code = 3;
  string grpc_message = 4;
}

message MultiSearchResponse {
  // Envelope status only: success does not imply every item succeeded.
  common.Status status = 1;
  // Same order and cardinality as input when envelope status is successful.
  repeated SearchOutcome items = 2;
}

Re-enter ordinary Search at the correct boundary

The callback uses the same entry chain as network Search calls, then calls Server.Search. This is the key difference between a safe orchestration primitive and an internal loop that skips authorization or quotas.

internal/distributed/proxy/multisearch.go · actual prototype source
	entry := proxyEntryInterceptor(limiter)
	search := func(ctx context.Context, req *milvuspb.SearchRequest) (*milvuspb.SearchResults, error) {
		// Fork mutable stats; the access-log interceptor similarly allocates
		// an independent object. Identity, deadlines and tracing are inherited.
		ctx = metrics.WithIndependentRPCStats(ctx)
		resp, err := entry(ctx, req, &grpc.UnaryServerInfo{Server: s, FullMethod: milvuspb.MilvusService_Search_FullMethodName},
			func(ctx context.Context, req any) (any, error) {
				return s.Search(ctx, req.(*milvuspb.SearchRequest))
			})
		if err != nil {
			return nil, err
		}
		result, ok := resp.(*milvuspb.SearchResults)
		if !ok || result == nil {
			return &milvuspb.SearchResults{Status: merr.Status(merr.WrapErrServiceInternalMsg("Search entry returned an invalid response"))}, nil
		}
		return result, nil
	}

Bounded workers, isolated requests, independent outcomes

internal/proxy/multisearch.go · actual prototype source
	for range min(e.limits.Parallelism, len(req.Items)) {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for ctx.Err() == nil {
				i := int(next.Add(1) - 1)
				if i >= len(req.Items) {
					return
				}
				select {
				case e.active <- struct{}{}:
				case <-ctx.Done():
					return
				}
				if ctx.Err() != nil {
					<-e.active
					return
				}
				item := req.Items[i]
				// Search and entry interceptors may mutate the request. Never share
				// caller-owned request pointers between workers (or retry attempts).
				search := proto.Clone(item.Search).(*milvuspb.SearchRequest)
				search.DbName = db
				result, err := e.search(ctx, search)
				<-e.active
				outcome := &multisearchpb.SearchOutcome{Id: item.Id, Result: result}
				if err != nil {
					s := status.Convert(err)
					outcome.Result = nil
					outcome.GrpcCode, outcome.GrpcMessage = int32(s.Code()), s.Message()
				} else if result == nil || result.Status == nil {
					outcome.Result = &milvuspb.SearchResults{Status: merr.Status(merr.WrapErrServiceInternalMsg("Search returned no result status"))}
				}
				// Reserve protobuf framing overhead as well as outcome bytes.
				if resultBytes.Add(int64(proto.Size(outcome)+16)) > int64(e.limits.MaxResponseBytes) {
					overflow.Store(true)
					cancel()
					return
				}
				out.Items[i] = outcome
			}
		}()
	}

The client really sends one request

The local adapter reuses PyMilvus's existing Search messages and adds one extension service stub. This is a functioning prototype method, not a claim that released MilvusClient already supports MultiSearch.

examples/multisearch/client.py · actual prototype source
    def multi_search(self, items, timeout=10):
        """Return all outcomes, including individual failures, without retrying."""
        request = multisearch_pb2.MultiSearchRequest(db_name=self.db_name)
        for item_id, search_request in items:
            request.items.add(id=item_id, search=search_request)
        return self._multi(request, timeout=timeout, metadata=self.metadata)

Public protocol ownership is intentionally separated for this prototype: the extension lives in the Milvus repository and imports the existing public Search messages. Graduation requires an agreed public protobuf/API location, SDK support and compatibility behavior.

Test execution notes and discarded runs

The final evidence is results.json, limits-results.json, performance.json and the final test logs. One intermediate benchmark was invalidated because a quota fault-injection test ran concurrently; the quota was restored and functional checks and performance were rerun separately. Initial unit-test environment issues (missing etcd and an unwritable default storage directory) were resolved with a dedicated etcd and a temporary local data path. A broader existing parameter test assumes a hardcoded storage path and fails under that override; the focused Proxy configuration and merr guard checks pass. The full repository test suite was not run.

Performance against ordinary Search

Each measured group performs the same 50 logical searches. Baselines use a persistent gRPC channel: sequential Search for reference and bounded client fan-out as the useful comparison. Parallel Search and MultiSearch both allow 16 searches per group and 64 active searches globally. There are no retries. Warmup is excluded; every returned item is checked for success.

Standalone Docker was limited to 16 CPUs and 32 GiB on a 128-logical-CPU host. Measurements were taken before the Kubernetes workload was deployed. Client CPU is Python process CPU; server CPU is the standalone container's cgroup CPU delta, including its background activity.

Observed at concurrency 1: median completion time fell from 60.25 ms to 21.67 ms (64.0% lower), with 2.75× the completed logical-search throughput. Client CPU per logical search fell by 96.4%. External RPC count fell 50×; the number of logical Search operations did not.
Interpret this as an orchestration microbenchmark. The dataset is small, searches are cheap, and Python client overhead is prominent. Each parallel/batch phase contains only 60 groups; high-concurrency MultiSearch phases last under one second. The p99 values are descriptive sample percentiles, not stable tail estimates. The baseline is this Python gRPC client, not the customer’s Baseten C runtime / REST client. This is neither sustained saturation capacity nor evidence of production speedup, server efficiency at scale, or a PSC reliability fix.

All seven final phases completed: 19,000 measured logical searches, zero observed errors. The likely mechanism is reduced Python/gRPC work and moving fan-out into the Go Proxy; the experiment does not isolate each cost with profiling. Larger vectors, ANN indexes, filters, larger outputs, heterogeneous slow items and a remote network should be tested next. A unary envelope still waits for all items, so a slow item controls completion latency.
